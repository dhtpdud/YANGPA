# 양파 메신저(가칭) 개발 계획서

Oct 19, 2026 · @Oh Seyoung

## 개요

양파 메신저(가칭)는 중앙 서버 없이 친구·크루 단위로 대화하고, 데이터를 얼마나 저장·제공·수신할지 사용자가 직접 정하는 디스코드형 P2P 메신저입니다. 1대1 공간에서 출발해 같은 환경 그대로 크루로 확장되며, 오가는 모든 데이터는 종단간 암호화됩니다.

설계 원칙은 여섯 가지입니다.

- **서버 없음**: 부트스트랩·릴레이·상시 시더도 누구나 띄울 수 있는 일반 노드로 대체합니다.
- **하나의 모델**: 1대1 공간은 멤버 2명짜리 크루로 다룹니다. 채널·암호화·동기화 코드가 하나로 유지되고, 크루 전환 시 데이터 이관이 없습니다.
- **경로는 데이터 종류로 나눔**: 음성·화면은 WebRTC, 메시지는 gossip 전파와 재동기화, 파일과 과거 기록은 조각 스웜으로 보냅니다. 인원수에 따라 경로를 바꾸지 않습니다.
- **사용자가 결정**: 무엇을 저장·제공·수신할지는 개인 설정(시더·피어)과 채널 설정(보안 등급, 과거 기록 공개)이 정합니다.
- **지킬 수 있는 것만 약속**: 휘발성·삭제·Tor 모드의 보장 범위와 한계를 UI에 정확히 표시합니다.
- **데몬 우선**: GUI·CLI·API·AI 연동이 모두 같은 코어 데몬의 클라이언트입니다.

## 용어 정의

네트워크상의 기기는 '노드', 데이터를 받아가는 사용자 역할은 '피어'로 구분해 씁니다. libp2p에서는 모든 기기를 peer라고 부르기 때문에, 문서와 코드에서 이 둘을 섞지 않습니다.

| 용어 | 뜻 |
| --- | --- |
| 노드 | 앱(코어 데몬)이 실행 중인 기기 하나. 네트워크 연결의 단위 |
| 사용자 | 신원 키 하나로 식별되는 사람. 노드 여러 대(PC, 폰)를 가질 수 있음 |
| 스페이스 | 두 친구 사이의 1대1 공간. 채널을 여러 개 가질 수 있고, 내부 구조는 멤버 2명짜리 크루와 같음 |
| 크루 | 디스코드 서버에 해당하는 커뮤니티 단위. 역할·권한·초대 기능을 가짐 |
| 채널 | 스페이스·크루 안의 대화방. 텍스트, 음성, 포럼 종류가 있음 |
| 시더 | 크루 내 다른 멤버가 요청하면 자기 데이터를 제공하는 역할. 제공 범위와 대역폭은 본인이 정함 |
| 피어 | 시더에게 데이터를 요청해 받는 역할. 받을 종류·우선순위·대역폭은 본인이 정함 |
| 이벤트 | 메시지, 반응, 수정, 채널·역할 변경 등 서명된 데이터 단위. 모든 동기화의 최소 단위 |
| 에포크 | 그룹 암호화 키가 한 번 바뀔 때까지의 구간. 멤버가 들고 날 때마다 새 에포크가 시작됨 |

시더와 피어는 동시에 켤 수 있는 독립 설정으로 설계합니다. 대부분의 사용자는 둘 다 켠 상태가 기본값입니다.

## 시스템 아키텍처와 기술 스택

코어 데몬 하나가 신원, 암호화, 저장, 동기화, 네트워크를 모두 맡고, 데스크톱 앱·CLI·AI 연동은 그 데몬에 붙는 클라이언트입니다. 그래서 AI 자동화와 사람의 조작이 같은 기능을 같은 권한 모델로 사용합니다.

음성·화면공유 미디어만 예외로 웹뷰의 WebRTC가 직접 상대와 주고받습니다. 이때도 연결 협상(SDP·ICE 교환)은 데몬의 libp2p 스트림을 거치므로 시그널링 서버가 필요 없습니다.

휘발성 데이터는 데몬 안에서도 RAM 저장소로만 가고, 디스크 저장소와는 코드 경로가 분리됩니다.

| 영역 | 선택 | 선택 이유 |
| --- | --- | --- |
| 코어 언어 | Rust | Tor 클라이언트(Arti)가 러스트 네이티브이고, 휘발성 채널에 필요한 메모리 제어(메모리 잠금, 해제 시 덮어쓰기)가 가능함 |
| P2P 네트워크 | rust-libp2p | QUIC·TCP 전송, Kademlia DHT, GossipSub, Circuit Relay v2, DCUtR 홀펀칭, AutoNAT을 한 라이브러리로 제공 |
| Tor | Arti + libp2p-community-tor | libp2p에 Tor 전송을 붙이고 onion 서비스로 연결을 받을 수 있음 |
| 그룹 암호화 | OpenMLS (RFC 9420) | 표준 MLS 구현. 멤버 변화에 따른 키 갱신 비용이 그룹 크기에 로그로 증가 |
| 로컬 저장 | SQLCipher + 파일 블롭 저장소 | 암호화된 SQLite. 첨부·이모지는 해시 이름의 암호화 파일로 분리 |
| 콘텐츠 주소 | BLAKE3 | 빠른 해시, 조각 단위 검증 스트리밍 지원 |
| 데스크톱 UI | Tauri + TypeScript | 러스트 코어와 직접 연결되고 앱 크기가 작음 |
| 미디어 | 웹뷰 WebRTC + Encoded Transform | 브라우저 미디어 스택 재사용. 프레임 단위 E2EE API가 주요 브라우저 엔진 모두에 들어감 |
| 로컬 API | JSON-RPC 2.0 (named pipe / Unix socket) + 이벤트 스트림 | GUI·CLI·MCP 서버가 같은 API 사용 |
| 모바일 | 2차 목표: 코어를 UniFFI로 바인딩 | 데스크톱 안정화 후 착수 |

## 신원·친구·프로필

사용자는 신원 키 하나를 갖고, 노드마다 만든 기기 키를 신원 키로 서명해 연결합니다. 네트워크에 드러나는 libp2p 주소 키는 이 둘과 분리해서, 외부 관찰자가 Tor 모드와 일반 모드의 같은 사용자를 연결 짓지 못하게 합니다.

### 키 구조

| 키 | 용도 | 공개 범위 |
| --- | --- | --- |
| 신원 키 (Ed25519) | 사용자 식별, 친구 관계와 크루 멤버십의 기준 | 친구·크루 멤버 (암호화 채널 안에서만) |
| 기기 키 | 노드별 서명과 MLS 참여. 신원 키가 서명한 기기 목록으로 배포 | 친구·크루 멤버 |
| 네트워크 키 (PeerId) | libp2p 연결용. 일반 모드와 Tor 모드에서 서로 다른 키 사용 | 네트워크 전체 |

- 신원 키 백업은 복구 문구 또는 암호화 백업 파일로 제공합니다. 분실하면 친구 관계를 복구할 수 없다는 점을 가입 시 안내합니다.
- 기기를 잃어버리면 다른 기기에서 그 기기 키를 폐기하고, 폐기 이벤트가 MLS 그룹에서 해당 기기를 제거합니다.
- 친구 사이에는 신원 키 지문을 비교하는 안전 번호 확인 화면을 둡니다.

### 친구 추가 링크

링크에는 신원 공개키, 1회용 토큰, 만료 시각, 접속 정보만 담습니다. 일반 모드라도 IP 주소는 넣지 않고 릴레이 경유 주소나 DHT 조회 키를 넣어서, 링크가 유출돼도 IP가 드러나지 않게 합니다. Tor 모드 사용자의 링크에는 onion 주소만 들어갑니다.

1. 사용자가 링크를 만듭니다. 1회용·다회용, 만료 시간을 고르고 언제든 폐기할 수 있습니다.
2. 받은 사람이 링크를 열면 앱이 접속 정보로 연결하고 토큰을 제출합니다.
3. 만든 사람의 노드가 토큰을 검증하고 수락 알림을 띄웁니다.
4. 수락하면 두 사람의 기기로 MLS 그룹을 만들고 스페이스가 생성됩니다.

### 프로필

- 프로필은 서명된 문서 하나입니다. 이름, 소개, 아바타, 배너, 테마 색, 상태 메시지를 담고, 이미지는 해시로 참조합니다.
- 친구 전체에 보이는 기본 프로필과, 크루마다 다른 닉네임·아바타를 쓰는 크루 프로필을 둡니다.
- 수정하면 버전 번호를 올려 전파하고, 받는 쪽은 가장 높은 버전을 씁니다.

### 친구 메모

친구 메모는 로컬 암호화 DB에만 저장하고 네트워크로 보내지 않습니다. 본인 기기들끼리는 '내 기기 전용 스페이스'(본인 기기만 멤버인 스페이스)로 메모와 설정을 동기화할 수 있게 합니다.

## 데이터 모델

스페이스와 크루는 같은 구조이고, 차이는 멤버 수와 역할 기능 사용 여부뿐입니다. 그래서 1대1 환경을 크루로 바꿀 때 종류 필드 하나만 바뀌고 데이터 이관은 없습니다.

### 공간 구조

공간(스페이스 또는 크루) 하나는 멤버 목록, 역할, 채널 트리(카테고리 포함), 커스텀 이모지, 설정을 가집니다. 이 정보는 모두 상태 이벤트로 기록됩니다.

### 채널 속성

| 속성 | 값 | 비고 |
| --- | --- | --- |
| 종류 | 텍스트, 음성, 포럼 | 이후 종류 추가를 고려해 확장 가능한 열거형으로 정의 |
| 보안 등급 | 일반, 휘발성 | 일반은 양측 디스크 저장, 휘발성은 RAM 전용 |
| 참여 방식 | 상시, 입장·퇴장 | 입장·퇴장 방식은 채널에 들어가 있는 동안만 대화 참여 |
| 채팅 수명 | 없음, 퇴장 시 삭제, N초 | 만료되면 RAM에서 해제(일반 등급은 디스크에서도 삭제) |
| 과거 기록 공개 | 공개, 비공개 | 새로 입장한 사용자가 입장 이전 기록을 볼 수 있는지 |

### 이벤트 DAG

- 모든 변경은 이벤트입니다. 메시지, 수정, 삭제 요청, 반응, 채널 생성·변경, 역할 변경, 멤버 가입·추방이 모두 해당합니다.
- 이벤트는 헤더(작성 기기 서명, 부모 이벤트 해시들, 채널 ID, 논리 시계, 종류)와 암호화된 본문으로 구성됩니다.
- 부모 해시로 인과 순서를 표현하고, 동시에 생긴 이벤트는 (논리 시계, 해시) 순으로 모든 노드가 같게 정렬합니다.
- 상태 이벤트(채널·역할·멤버)는 모든 멤버가 반드시 받고, 메시지 이벤트는 시더·피어 설정을 따릅니다.
- 첨부는 이벤트에 해시와 복호화 키만 싣고, 실제 파일은 조각 저장소에서 따로 받습니다.

### 빈 구간 허용

시더가 특정 채팅을 제공하지 않거나 피어가 일부 종류를 받지 않으면, 부모가 없는 이벤트가 생깁니다. 이 경우 오류로 처리하지 않고 '받지 않은 기록' 구간으로 표시하며, 나중에 다른 시더에게서 채울 수 있게 합니다.

## 종단간 암호화

그룹 키 합의는 MLS(RFC 9420)로 통일하고, 채널마다 MLS에서 파생한 키로 메시지·파일·미디어를 암호화합니다. 1대1 스페이스도 같은 방식이라 양측의 기기 전체가 하나의 MLS 그룹이 됩니다.

### 그룹과 커밋

- MLS 그룹 하나가 공간(스페이스·크루) 하나에 대응하고, 그룹의 구성원은 사용자가 아니라 기기입니다.
- MLS는 멤버 변경(커밋)의 순서를 정해주는 주체를 가정합니다. 서버가 없으면 두 커밋이 동시에 나와 그룹 상태가 갈라질 수 있습니다.
- 초기 버전은 공간마다 커밋 확정 노드를 둡니다(크루는 소유자·관리자 노드). 확정 노드가 오프라인이면 멤버 변경은 대기 상태가 됩니다.
- 탈중앙 환경용 MLS 확장(DMLS)은 IETF 초안 단계라서, 표준화 진행을 보고 P8에서 도입을 검토합니다.

### 채널 키

- 일반 채널의 키는 MLS 그룹 비밀에서 채널별로 파생합니다.
- 특정 역할만 볼 수 있는 비공개 채널은 그 채널 멤버만으로 별도 MLS 그룹을 운영합니다. 크루 전체 키로 암호화하면 권한 없는 멤버도 복호화할 수 있기 때문입니다.

### 기록 키 (과거 기록 공개용)

MLS는 새 멤버가 가입 이전 메시지를 읽지 못하도록 설계되어 있어서, '과거 기록 공개' 기능과 충돌합니다. 이를 위해 일반 등급 채널의 메시지는 기간별로 회전하는 '기록 키'로 암호화하고, 기록 키 자체를 MLS로 배포합니다.

- 과거 기록 공개 채널에 새 멤버가 들어오면, 권한 있는 시더가 과거 기록 키를 새 멤버에게 암호화해 전달합니다.
- 비공개 채널이면 기록 키를 전달하지 않습니다. 시더가 데이터를 실수로 보내도 새 멤버는 복호화할 수 없어 이중으로 보호됩니다.
- 대가: 기록 키를 보관하는 만큼 해당 채널의 전방 보안이 약해집니다. 과거 기록 비공개가 기본값입니다.

### 휘발성 채널 키

휘발성 채널은 기록 키를 쓰지 않고 에포크 키만 쓰며, 키도 RAM에만 둡니다. 멤버가 퇴장하면 즉시 키를 갱신합니다.

### 미디어

음성·화면공유는 WebRTC Encoded Transform으로 프레임마다 암호화하고, 키는 MLS에서 파생합니다. 디스코드가 음성·영상 E2EE(DAVE)에 쓰는 것과 같은 구조라서, 나중에 SFU를 도입해도 SFU는 내용을 볼 수 없습니다.

### 로컬 저장과 삭제

- 디스크 데이터는 SQLCipher로 암호화하고, DB 키는 OS 키 저장소(Windows 자격 증명 관리자, macOS 키체인)에 두며 선택적으로 앱 암호를 추가합니다.
- 메시지마다 별도 키를 두고, 삭제·수명 만료 시 그 키를 폐기합니다(암호학적 삭제). SSD처럼 덮어쓰기가 보장되지 않는 저장 장치에서도 복구할 수 없게 하기 위해서입니다.

## 휘발성 채널과 채팅 수명

휘발성 채널은 메시지·키·첨부를 디스크에 쓰지 않고 RAM에만 두며, 수명이 끝나면 메모리를 덮어써서 해제합니다. 다만 OS 알림, 웹뷰 캐시, 스왑까지 막아야 약속이 지켜지므로 아래 항목을 구현과 검증 대상으로 둡니다.

### 구현

- **분리된 저장 경로**: 휘발성 데이터는 전용 메모리 저장소에만 들어가고, DB·로그·캐시로 가는 코드 경로와 타입 단위로 분리합니다. 실수로 디스크에 쓰는 코드가 컴파일되지 않게 하는 것이 목표입니다.
- **암호문 보관, 키만 잠금**: 휘발성 내용은 RAM 안에서도 암호문으로 두고, 복호화 키만 잠긴 메모리(VirtualLock, mlock)에 둡니다. OS의 메모리 잠금 한도가 작기 때문이며, 암호문이 스왑으로 내려가도 키 없이는 읽을 수 없습니다. 화면에 표시할 때만 복호화하고, 해제할 때 키와 평문 버퍼를 0으로 덮어씁니다.
- **수명 타이머**: 데몬이 관리합니다. 기기 간 시계 차이를 피하려고 각 기기는 수신 시점 기준으로 N초를 계산합니다.
- **퇴장 시 삭제**: 사용자가 채널에서 나가면 그 사용자 기기의 채널 내용이 즉시 해제됩니다.
- **늦게 입장한 사용자**: 과거 기록 공개가 켜져 있으면, 지금 채널 안에 있는 멤버의 RAM에서 아직 수명이 남은 메시지만 받습니다.
- **재시작과 크래시**: 앱이 종료되면 휘발성 내용은 전부 사라집니다.

### 보장 범위 밖 경로와 대응

| 경로 | 위험 | 대응 |
| --- | --- | --- |
| OS 알림 | 알림 센터가 미리보기 내용을 디스크에 저장 | 휘발성 채널은 내용 없는 알림만 표시 |
| 웹뷰 캐시 | 이미지·영상과 커스텀 프로토콜 응답이 웹뷰 디스크 캐시에 남을 수 있음 | 메모리 전용 렌더링(blob URL), 커스텀 프로토콜 응답에 캐시 금지 헤더, 디스크 캐시 비활성, 자동 누출 테스트 |
| 스왑·최대 절전 | RAM 내용이 디스크로 내려감 | 키만 메모리 잠금, 내용은 암호문이라 스왑돼도 읽을 수 없음. 최대 절전 파일에는 키도 기록될 수 있어 설정 화면에 안내 |
| 크래시 덤프 | 메모리 내용이 덤프 파일로 저장 | 앱 프로세스의 덤프 생성 비활성 |
| 클립보드 | 복사한 내용이 OS 클립보드 기록에 남음 | 복사 시 경고, 복사 제한 옵션 |
| 화면 캡처 | 상대가 스크린샷·녹화 | '사용자가 따로 기록하는 경우'에 해당. 캡처 제외 창 옵션을 제공하되 완전 차단은 불가하다고 명시 |
| 개조된 클라이언트 | 상대가 앱을 고쳐 내용을 저장 | 기술적으로 막을 수 없음. 신뢰하는 상대와만 쓰도록 안내 |

### 일반 등급의 채팅 수명

일반 등급 채널에 수명을 설정하면, 만료된 메시지는 메시지별 키를 폐기해 디스크에서도 복구할 수 없게 합니다. 이 조합을 허용할지는 미결정 사항입니다.

## 동기화 엔진

동기화는 실시간 전파, 따라잡기, 파일 스웜, 상태 동기화 네 계층으로 나누고, 시더·피어 설정은 따라잡기와 파일 스웜에 적용합니다. 실시간 전파는 그 순간 온라인인 멤버 모두에게 가므로 개인 설정과 무관하며, 중계 트래픽에는 별도 상한을 둡니다.

| 계층 | 대상 | 방식 | 시더·피어 설정 |
| --- | --- | --- | --- |
| 실시간 전파 | 새 이벤트 | 크루는 GossipSub 토픽, 스페이스는 직접 스트림 | 적용 안 함 |
| 따라잡기 | 오프라인 동안 놓친 이벤트 | 부모 해시 추적 + 시간 구간 지문 비교로 빠진 것만 요청 | 적용 |
| 파일 스웜 | 첨부, 이모지, 봉인된 과거 기록 묶음 | BLAKE3 조각을 여러 시더에게서 병렬 수신 | 적용 |
| 상태 동기화 | 채널, 역할, 멤버, 이모지 목록 | 따라잡기와 같은 방식 | 필수, 제외 불가 |

### 시더 설정

- 제공 범위: 데이터 종류(텍스트, 이미지, 영상, 파일, 이모지, 과거 기록 묶음) × 채널 × 개별 메시지 제외까지 지정합니다.
- 송신 대역폭 상한과 동시 전송 수를 지정합니다.
- 시더는 자기가 가진 데이터만 제공할 수 있습니다. 피어로서 받지 않은 데이터는 제공 목록에도 나타나지 않습니다.

### 피어 설정

- 받을 데이터 종류, 종류별 우선순위, 수신 대역폭 상한, 자동 다운로드 크기 한도를 지정합니다.
- 요청 순서: 상태 동기화 → 보고 있는 채널의 최근 이벤트 → 우선순위에 따른 첨부 → 스크롤할 때 과거 기록을 지연 로드합니다.

### 요청 처리 순서

시더 노드는 요청을 받으면 다음 순서로 검사하고, 하나라도 실패하면 거절합니다.

1. 요청자가 공간의 현재 멤버인가
2. 요청자가 그 채널을 볼 권한이 있는가
3. 요청한 이벤트가 요청자의 입장 이전이라면, 채널의 과거 기록 공개가 켜져 있는가
4. 시더의 제공 범위에 포함되는가
5. 대역폭 여유가 있는가 (없으면 대기열)

### 가용성

- 아무도 제공하지 않는 데이터는 사라집니다. 관리자 화면에 채널별 '시더 커버리지'(그 데이터를 제공하는 온라인 시더 수)를 보여주고, 0이 되면 경고합니다.
- CLI 헤드리스 모드로 NAS나 VPS에서 상시 시더를 운영할 수 있게 합니다.
- 선택 기능: 복호화 키 없이 암호화된 데이터만 보관·제공하는 '보관 전용 노드'. 내용을 볼 수 없는 상시 저장소 역할입니다.

### 스웜 보호

- 크루 멤버끼리만 연결하는 닫힌 스웜을 씁니다. 공개 DHT나 트래커에 크루 데이터를 올리지 않습니다.
- 조각은 암호화된 상태로 교환합니다.
- 서명, 멤버십, 권한, 전송 빈도를 검사해 실패한 피어는 점수를 깎아 연결에서 밀어냅니다.

## Tor 모드

Tor 모드는 '내 IP를 숨기는' 개인 설정이고, 켜든 끄든 모든 노드는 내장 Tor 클라이언트(Arti)로 onion 주소에 접속할 수 있어야 합니다. 그래야 Tor 사용자와 일반 사용자가 같은 스페이스·크루에서 대화할 수 있습니다.

### 켜면 바뀌는 것

- 나가는 연결은 모두 Arti를 거치고, 들어오는 연결은 onion 서비스로 받습니다.
- onion 서비스는 NAT 뒤에서도 접속을 받을 수 있어서, Tor 모드에서는 홀펀칭과 릴레이가 필요 없습니다.
- 네트워크 키(PeerId)를 Tor 모드 전용으로 바꿉니다. 친구는 암호화 채널 안에서 신원 키로 같은 사람임을 확인합니다.

### 함께 꺼야 하는 것

libp2p Tor 전송 라이브러리 스스로, 전송만 바꿔 끼우면 익명성이 생기지 않는다고 경고합니다. Tor 모드에서는 다음을 모두 끕니다.

- identify 프로토콜의 주소 광고
- DHT에 일반 IP 주소 등록
- mDNS(같은 네트워크 탐색), AutoNAT, DCUtR 홀펀칭
- 링크 미리보기의 직접 조회 (Tor 경유로만 조회)
- WebRTC 음성·화면공유 (아래)

### 음성·화면공유

WebRTC는 UDP를 쓰는데 Tor는 TCP만 전달하므로, Tor 모드에서 음성·화면공유를 Tor로 보낼 수 없습니다. 기본은 비활성으로 두고, 사용자가 동의하면 일반망 TURN 서버를 경유해 참여하게 합니다. 이 경우 실제 IP는 TURN 운영자에게만 보이며, 이 선택지를 넣을지는 미결정 사항입니다.

### 성능과 검증

- Tor 경유는 지연이 크게 늘어나므로, Tor 모드의 파일 스웜 기본 대역폭을 낮게 잡고 텍스트를 우선합니다.
- Tor 모드 전용 통합 테스트에서 패킷을 캡처해, 일반 IP로 나가는 연결이 0건인지 자동으로 확인합니다.

### 참고 사례

Quiet는 Tor 위에서 libp2p와 CRDT로 팀 채팅을 동기화하는 오픈소스 앱입니다. 커뮤니티별로 분리된 망, onion 주소만 쓰는 연결 등 이 계획과 겹치는 부분이 많아 설계 검토 시 참고합니다.

## 음성·화면공유

음성 채널은 WebRTC 미디어로 처리하고, 연결 협상(SDP·ICE 교환)은 이미 연결된 libp2p 스트림으로 주고받아 별도 시그널링 서버를 두지 않습니다. 병목은 화면공유를 몇 명에게 몇 번 인코딩해 보내느냐이므로, 토폴로지와 화면공유 전송 범위를 함께 설계합니다.

### 토폴로지

- 소규모 통화는 메시(참가자끼리 모두 직접 연결)로 처리합니다. 음성만 있으면 인원이 늘어도 부담이 작습니다.
- 참가자가 기준 인원을 넘으면 SFU로 전환합니다. SFU는 회선이 좋은 참가자 노드 또는 크루가 운영하는 노드가 맡습니다. 기준 인원은 P4에서 측정해 정합니다.
- 이 전환은 통화 참가자 목록을 통화 안의 모두가 똑같이 알고 있어서 노드마다 판단이 엇갈리지 않습니다.

### 화면공유

- '보기'를 누른 참가자에게만 영상을 보냅니다(디스코드 Go Live 방식). 인코딩 수가 통화 인원이 아니라 실제 시청자 수가 됩니다.
- 비디오 트랜시버를 미리 확보하고 트랙 교체로 켜고 꺼서, 화면공유를 시작할 때마다 재협상하지 않습니다.
- 콘텐츠 힌트로 용도를 구분합니다. 문서·코드는 선명도 우선, 게임은 프레임 우선입니다.
- 시스템 소리를 함께 공유할 때는 앱 자신의 출력(다른 참가자 목소리)을 캡처에서 빼야 에코가 생기지 않습니다. Windows는 프로세스 단위 루프백 캡처로 처리합니다.

### 통화 중 데이터

- 화면 위 포인터, 음소거 상태처럼 통화 중에만 의미 있는 정보는 WebRTC 데이터 채널로 보냅니다.
- 통화 중 입력한 채팅은 텍스트 채널 경로로 보내서, 통화가 끝나도 남고 통화에 없는 멤버도 볼 수 있게 합니다.

### 프라이버시와 플랫폼

- WebRTC 연결 후보에는 실제 IP가 담겨 상대에게 노출됩니다. 일반 모드에도 'IP 숨기기'(TURN 경유만 허용) 옵션을 둡니다.
- Windows(WebView2)와 macOS(WKWebView)는 웹뷰 WebRTC를 쓰고, 리눅스(WebKitGTK)는 WebRTC 지원이 불안정할 수 있어 네이티브 미디어 스택을 따로 검토합니다.

## 텍스트 채널 기능

텍스트 채널은 메시지·첨부·링크·반응을 모두 이벤트로 다루고, 큰 데이터는 이벤트에 해시만 실은 뒤 파일 스웜으로 받습니다. 링크 미리보기는 보내는 쪽이 만들어서, 받는 쪽이 외부 사이트에 접속하지 않게 합니다.

### 첨부

- 이미지·영상·파일은 보내는 쪽이 썸네일과 메타데이터(크기, 길이, 해상도)를 만들어 이벤트에 넣습니다. 받는 쪽은 원본 없이 미리보기를 볼 수 있습니다.
- 원본은 피어의 우선순위와 자동 다운로드 한도에 따라 받습니다. 첨부 용량 상한은 미결정 사항입니다.

### 링크 임베딩

- 보내는 쪽이 제목, 설명, 썸네일을 조회해 암호화된 미리보기로 첨부합니다. 받는 쪽의 IP가 링크 사이트에 노출되지 않습니다.
- Tor 모드 사용자가 보낼 때는 Tor 경유로 조회합니다.
- 유튜브 같은 미디어 링크의 플레이어는 '눌러서 불러오기'로 둡니다. 누르기 전에는 외부 접속이 일어나지 않습니다.
- 채널별로 미리보기 생성을 끌 수 있고, 휘발성 채널은 기본값이 꺼짐입니다.

### 반응

반응은 대상 메시지 해시와 이모지를 담은 이벤트입니다. 유니코드 이모지와 커스텀 이모지를 모두 지원합니다.

### 커스텀 이모지

- 메시지 안의 표기는 디스코드 양식을 따릅니다. 정지 이모지는 `<:이름:ID>`, 애니메이션 이모지(gif, 애니메이션 webp)는 `<a:이름:ID>`입니다.
- ID는 이미지 BLAKE3 해시의 앞 64비트를 10진수로 적어, 디스코드의 숫자 ID 양식과 맞춥니다. 같은 이미지는 어디서 올려도 같은 ID가 됩니다.
- 지원 확장자는 png, gif, webp이고, 크기 상한은 디스코드와 비슷한 수준으로 정합니다.
- 이모지는 스페이스·크루에 속합니다. 1대1 스페이스에서도 만들고 쓸 수 있습니다.
- 다른 공간의 이모지를 쓰면, 받는 쪽은 ID로 스웜에서 이미지를 받아 표시합니다. 이 교차 사용을 허용할지는 미결정 사항입니다.

### 수정과 삭제

- 수정은 원본을 가리키는 수정 이벤트로, 삭제는 삭제 요청 이벤트로 처리합니다.
- 정상 클라이언트는 삭제 요청을 받으면 메시지 키를 폐기합니다. 이미 받아간 상대 기기에서 강제로 지울 수는 없다는 점을 UI에 표시합니다.

### 포럼

- 포럼 채널의 게시글 하나는 제목, 본문, 태그를 가진 하위 스레드입니다.
- 태그 목록, 고정, 잠금은 채널 상태 이벤트로 관리하고, 최근 활동순·작성일순 정렬을 제공합니다.
- 피어는 게시글 목록(제목, 태그, 작성자)만 먼저 받고, 본문과 댓글은 게시글을 열 때 받습니다.

## 크루 관리

크루 권한은 디스코드식 역할과 권한 비트로 표현하고, 모든 변경을 서명된 상태 이벤트로 남겨 각 노드가 같은 규칙으로 검증합니다. 서버가 없으므로 '누가 그 시점에 그 권한을 가졌는가'를 모든 노드가 스스로 판단할 수 있어야 합니다.

### 역할과 권한

- 역할은 이름, 색, 순위, 권한 비트를 가집니다. 권한에는 채널 관리, 역할 관리, 추방, 메시지 관리, 초대 생성, 이모지 관리, 음성 관리 등이 있습니다.
- 채널마다 역할별 권한을 덮어쓸 수 있습니다.
- 이벤트를 받으면 작성자가 DAG상 그 시점에 해당 권한을 가졌는지 확인하고, 없으면 무시합니다.
- 동시에 일어난 권한 변경(예: 관리자 둘이 동시에 서로를 추방)은 (역할 순위, 논리 시계, 해시) 순서의 결정론적 규칙으로 해소합니다. Matrix의 상태 해소 알고리즘을 참고합니다.
- 크루를 만든 사람의 신원 키가 소유자이며, 소유권 이전도 서명된 이벤트로 처리합니다.

### 초대 링크

초대 링크는 크루 ID, 초대 토큰, 만료 시각, 사용 횟수, 가입 시 부여할 역할, 접속 정보를 담습니다. 초대 생성 권한이 있어야 만들 수 있고 언제든 폐기할 수 있습니다.

### 1대1에서 크루로 전환

1. 한쪽이 전환을 요청하고 상대가 동의합니다. 기존 대화가 새 멤버에게 노출될 수 있어서 양측 동의를 필수로 합니다.
2. 공간 종류만 스페이스에서 크루로 바뀌고, 채널·이모지·기록은 그대로 유지됩니다.
3. 기존 채널의 과거 기록 공개는 '비공개'로 시작하고, 두 사람이 합의해 바꿀 수 있습니다.
4. 전환 후 두 사람의 초기 역할(공동 관리자 또는 요청자 소유)은 미결정 사항입니다.

혼자 크루를 먼저 만들 때는 멤버 1명짜리 크루로 시작하고 링크로 초대합니다.

### 모더레이션의 한계

추방된 멤버는 MLS 커밋으로 이후 데이터를 받지 못하지만, 이미 받은 데이터는 계속 가지고 있습니다. 탈중앙 구조의 본질적 한계라서 관리 화면에 명시합니다.

## API·CLI·AI 연동

코어 데몬이 로컬 API를 제공하고 CLI와 GUI가 같은 API를 쓰며, AI 연동은 그 위에 MCP 서버를 얹어 구현합니다. AI가 다른 멤버의 메시지를 읽게 되는 만큼, 휘발성 채널 접근과 파괴적 작업에는 별도 안전장치를 둡니다.

### 로컬 API

- JSON-RPC 2.0을 Windows named pipe와 Unix socket으로 제공하고, 새 메시지·멤버 변경 같은 이벤트는 구독 스트림으로 보냅니다.
- 원격 접근은 기본 비활성입니다. 켜려면 사용자가 명시적으로 허용해야 합니다.
- API 토큰마다 범위를 지정합니다. 읽기·쓰기, 특정 크루, 관리 권한 종류 단위이며, 모든 호출은 감사 로그에 남습니다.

### CLI

CLI 명령 이름은 가칭이며, 앱의 모든 기능을 같은 구조로 노출합니다.

```bash
yangpa crew create "게임 모임"
yangpa channel create --crew "게임 모임" --type text --name 공지
yangpa channel create --crew "게임 모임" --type text --name 비밀 --volatile --join-leave --ttl 30s
yangpa role create --crew "게임 모임" --name 운영진 --perms manage_channels,kick
yangpa invite create --crew "게임 모임" --expires 24h --uses 10
yangpa seed set --crew "게임 모임" --types text,emoji --upload-limit 2MB/s
```

헤드리스 모드(GUI 없이 데몬과 CLI만 실행)를 지원해서 NAS·VPS에서 상시 시더를 운영할 수 있게 합니다.

### AI 연동

- MCP 서버가 API를 도구로 노출합니다. 채널·역할 관리, 초대 생성, 시더 설정, 채널 요약 같은 작업을 AI가 수행할 수 있습니다.
- 크루에서 자동화가 동작 중이면 멤버 목록에 자동화 표시를 붙여 투명하게 알립니다.

### AI 안전 규칙

- **휘발성 채널은 API 읽기 기본 거부**: AI가 내용을 읽는 순간 사실상 '기록'이 됩니다. 사용자가 채널 단위로 명시 허용할 때만 열립니다.
- **메시지는 지시가 아니라 데이터**: 다른 멤버가 쓴 메시지에 AI를 조종하는 문장이 섞일 수 있습니다(프롬프트 인젝션). 추방, 삭제, 권한 변경, 초대 생성 같은 작업은 사람 확인을 필수로 합니다.
- **최소 권한 토큰**: AI용 토큰은 필요한 크루와 작업으로 범위를 좁혀 발급합니다.

## 성능·최적화

성능은 목표 수치를 먼저 정하고, 그 목표를 로드맵 완료 기준과 CI 벤치마크로 지키는 방식으로 관리합니다. 코어 데몬이 상시 실행되는 구조라서, 특히 유휴 상태의 자원 사용량이 체감 품질을 좌우합니다.

### 성능 목표

아래 값은 제안값이며, P0에서 기준선을 측정한 뒤 확정합니다.

| 항목 | 제안 목표 | 확인 단계 |
| --- | --- | --- |
| 메시지 전달 지연, 직접 연결 (p95) | 300ms 이하 | P1 |
| 앱 실행부터 대화 목록 표시까지 | 1초 이하 (네트워크 연결 전) | P1 |
| 메시지 전달 지연, Tor 모드 (p95) | 3초 이하 | P2 |
| 메시지 목록 스크롤 | 메시지 1만 개 채널에서 60fps 유지 | P3 |
| 유휴 상태 데몬 자원 | 메모리 150MB 이하, CPU 1% 미만 | P3 |
| 음성 지연, 직접 연결 메시 (입에서 귀까지) | 200ms 이하 | P4 |
| 크루 가입 후 사용 가능까지 | 상태와 최근 메시지 표시 10초 이하 | P6 |

### 휘발성 채널 메모리

OS는 잠글 수 있는 메모리 양에 작은 기본 한도를 둡니다. 그래서 휘발성 내용은 RAM 안에서도 암호문으로 두고 복호화 키만 잠긴 메모리에 둡니다. 잠금 메모리가 키 크기만큼만 필요해져, 큰 이미지·영상도 휘발성 채널에서 보낼 수 있습니다.

### 데몬과 UI 사이 (Tauri)

- 이미지·파일 같은 바이너리는 JSON IPC 대신 커스텀 프로토콜로 넘깁니다. JSON 직렬화 비용을 피하기 위해서이며, 응답에는 캐시 금지 헤더를 붙여 휘발성 누출 검사 대상에 포함합니다.
- 새 메시지·상태 변경 이벤트는 화면 프레임 단위로 묶어 한 번에 보냅니다.
- 메시지 목록은 보이는 부분만 그리는 가상 스크롤을 쓰고, 이미지 디코딩은 메인 스레드 밖에서 처리합니다.

### 시작 속도

- 화면은 로컬 DB에서 즉시 띄우고, 네트워크 연결과 따라잡기는 백그라운드에서 진행합니다.
- Arti는 첫 실행 때 Tor 네트워크 정보를 받느라 시간이 걸립니다. 디렉터리 캐시를 유지하고 연결 진행 상태를 화면에 표시합니다.
- 최근 연결에 성공한 노드 주소를 캐시해, 재실행 시 부트스트랩 조회를 건너뜁니다.

### 여러 크루에 가입했을 때

- libp2p 연결 하나를 여러 크루·스페이스가 공유하고, 연결 관리자로 전체 연결 수에 상한을 둡니다.
- 앱이 최소화되면 저전력 모드로 바꿉니다. gossip 참여를 최소화하고, 시딩 대역폭을 줄이고, 보이지 않는 크루의 첨부 다운로드를 멈춥니다.
- 오래 열지 않은 크루는 실시간 전파 구독을 끊는 휴면 상태로 두고, 다시 열 때 따라잡기로 동기화합니다.

### 저장소

- SQLCipher는 WAL 모드로 쓰고, (채널, 논리 시계)와 이벤트 해시에 인덱스를 둡니다.
- 받은 이벤트는 트랜잭션 단위로 묶어 씁니다. 메시지 하나마다 디스크에 쓰지 않습니다.
- 첨부는 DB 밖 블롭 파일로 두어 DB 크기를 작게 유지합니다.

### 네트워크와 동기화

- 따라잡기 요청은 묶어서 보내고, 이벤트 묶음은 압축한 뒤 암호화합니다. 메시지 하나 단위로 압축하면 길이 정보가 새어 나갈 수 있어 묶음 단위로만 압축합니다.
- 메시지 ID로 중복을 걸러, 같은 이벤트를 두 번 검증·저장하지 않습니다.
- 파일 스웜은 희귀 조각부터 요청하고, BLAKE3 검증 스트리밍으로 받는 즉시 조각을 검증합니다. 조각 크기는 P3에서 측정해 정합니다.
- 초대 링크로 여러 명이 동시에 가입하면 멤버 추가를 MLS 커밋 하나로 묶어 처리합니다.

### 음성·화면공유

- 음성은 Opus DTX로 말하지 않을 때 전송을 멈춰 대역폭을 줄입니다.
- 화면공유는 하드웨어 인코딩을 우선하고, SFU 단계에서는 simulcast로 시청자 회선에 맞는 화질을 보냅니다.

### 측정과 회귀 방지

- 러스트 벤치마크(암호화, 이벤트 저장, 동기화 비교)를 CI에서 돌려, 기준선보다 느려지면 빌드를 실패 처리합니다.
- 지연과 패킷 손실을 흉내 낸 네트워크 시뮬레이터로 노드 수백 개 규모의 크루를 테스트합니다(P6).
- 앱 안에 성능 계측(전달 지연, 메모리, 프레임 시간)을 넣되, 외부로 보내지 않고 로컬 진단 화면에서만 보여줍니다.

## 개발 로드맵

개발은 기술 검증(P0)부터 확장(P8)까지 아홉 단계로 진행하고, 각 단계는 완료 기준을 통과해야 다음으로 넘어갑니다. 휘발성 채널과 Tor 모드를 크루보다 먼저 만드는 이유는, 이 둘이 저장 경로와 네트워크 구조 전체를 제약하기 때문입니다.

강조한 P2가 이 앱의 정체성을 결정하는 단계입니다. 단계별 기간은 팀 규모와 Rust 숙련도에 따라 크게 달라지므로, P0 결과를 보고 확정합니다. 각 단계의 완료 기준에는 성능 목표 표에서 그 단계에 해당하는 항목 충족이 함께 포함됩니다.

## 리스크와 미결정 사항

가장 큰 리스크는 앱의 핵심 약속인 휘발성과 Tor 모드가 구현 실수 하나로 깨질 수 있다는 점입니다. 그래서 두 기능은 자동 누출 테스트를 단계 완료 기준으로 둡니다.

### 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 휘발성 내용의 디스크 누출 (웹뷰 캐시, OS 알림 등) | 핵심 약속 훼손 | P0에서 누출 검사 도구 제작, P2 완료 기준으로 사용 |
| Tor 모드 IP 누출 | 사용자 위치 노출 | 끄기 목록 강제, 패킷 캡처 자동 테스트 |
| 시더 부재로 기록 소실 | 크루 기록 유실 | 시더 커버리지 경고, 헤드리스 시더, 보관 전용 노드 |
| 탈중앙 MLS 커밋 충돌 | 그룹 상태 분기, 일부 멤버 복호화 실패 | 커밋 확정 노드, DMLS 표준화 추적 |
| 불법·유해 콘텐츠 유통 | 시더가 남의 콘텐츠를 보관·배포하게 되어 법적 부담 발생 | 시더 기본값을 '본인이 연 채널만'으로, 메시지 단위 제외, 신고·차단 기능 |
| Rust 학습 비용과 개발 규모 | 일정 지연 | P0에서 핵심 라이브러리 숙련, 단계별 범위 엄수 |
| 리눅스 WebKitGTK WebRTC 불안정 | 리눅스 음성 기능 제한 | 네이티브 미디어 스택 검토 |
| AI 연동의 프롬프트 인젝션 | 의도치 않은 관리 작업 실행 | 파괴적 작업 사람 확인, 최소 권한 토큰 |

### 미결정 사항

- [ ] 일반 등급 채널에도 채팅 수명을 허용할지
- [ ] Tor 모드 사용자에게 TURN 경유 음성 참여를 허용할지
- [ ] 첨부 파일 용량 상한
- [ ] 커스텀 이모지 크기 상한, 다른 공간 이모지의 교차 사용 허용 여부
- [ ] 1대1에서 크루로 전환한 뒤 두 사람의 초기 역할
- [ ] 음성 채널의 메시→SFU 전환 기준 인원 (P4 측정 후)
- [ ] 정식 앱 이름, 링크 스킴
- [ ] 오픈소스 공개 여부와 라이선스 (프라이버시 앱은 코드 공개가 신뢰의 근거가 됨)
- [ ] 모바일 착수 시점
