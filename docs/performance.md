# 성능: 목표·측정·회귀 검사

[기획서](plan.md) "성능·최적화"의 목표를 어떻게 재고 지키는지 적습니다. 숫자는 아래 "측정 환경"에서 잰 기준선입니다.

## 목표와 확인 방법

| 항목 | 목표 | 확인 | 기준선(측정 환경) |
| --- | --- | --- | --- |
| 메시지 전달 지연, 직접 연결(P2P 전용 채널·상시 노드) (p95) | 300ms 이하 | `tests/perf.rs::direct_delivery_p95` | p50 3.5ms, p95 5.0ms, 최대 22ms(200개) |
| 앱 실행부터 대화 목록 표시까지 | 1초 이하(네트워크 연결 전) | `tests/perf.rs::start_to_space_list` | 프로세스 안 68ms, `yangpad` 169ms(공간 11개·메시지 3000개) |
| 유휴 상태 데몬 자원 | 메모리 150MB 이하, CPU 1% 미만 | `tests/perf.rs::idle_daemon_resources` | RSS 39.9MB, CPU 0.10%(30초) |
| 크루 가입 후 사용 가능까지 | 상태와 최근 메시지 표시 10초 이하 | `tests/perf.rs::crew_join_to_usable` | 88ms(기록 200개), 들어온 뒤 첫 메시지 전달 61ms |
| 메시지 전달 지연, Tor(앱 기본) (p95) | 3초 이하 | 재지 않음(실제 Tor 망 필요, 아래 "빈칸") | - |
| 메시지 목록 스크롤 | 1만 개 채널에서 60fps | 재지 않음(앱 쪽) | - |
| 음성 지연(입에서 귀까지) | 200ms 이하 | 재지 않음(앱 WebRTC 쪽) | - |
| 암호화·이벤트 저장·동기화 비교의 회귀 | 기준선보다 느려지면 실패 | `yangpa-bench gate`(CI `bench.yml`) | 아래 표 |
| 노드 수백 개 규모 크루(지연·손실 흉내) | 실제 Tor 40노드 크루 토픽 p95 ≤ 3초(대형 크루 12단계): 2,967ms로 맞음 | `tests/perf.rs::scaled_crew_simulation` | 아래 "여러 노드 시뮬레이션" |

CPU는 한 코어를 100%로 본 값입니다(`diag.metrics`의 `cpu_percent`).

## 성능 목표 시험 (`crates/yangpa-daemon/tests/perf.rs`)

최적화 빌드에서 하나씩 돌려야 의미가 있어 모두 `#[ignore]`입니다. CI는 `bench.yml`의 `targets` 작업이 돌리고, 목표를 넘으면
실패합니다.

```sh
cargo test --profile perf -p yangpa-daemon --test perf -- --ignored --test-threads=1 --nocapture --skip scaled_crew_simulation
```

| 시험 | 재는 것 |
| --- | --- |
| `direct_delivery_p95` | 친구 1:1 공간에서 A가 `message.send`를 부르기 직전부터 B에 `message.new`가 올 때까지(서명·암호화·저장·전파·검증·적용 전부). 데우기 10개 뒤 200개를 차례로 보내 p50·p95·최대를 냄(B의 `diag.metrics` p95도 함께 찍음) |
| `start_to_space_list` | 친구 1:1(양쪽 메시지 500개씩)과 크루 10개(메시지 200개씩), 모두 3000개가 든 DB로 다시 시작해 `space.list`가 돌아올 때까지. 프로세스 안(`Node::start`)과 `yangpad` 프로세스(실행 → 소유자 토큰으로 API 인증 → `space.list`, SQLCipher 메모리 보호 등 실제 설정) 둘 다 |
| `idle_daemon_resources` | 친구 하나와 연결된 `yangpad`가 메시지를 주고받은 뒤 할 일 없이 30초 있을 때의 RSS와 CPU(`diag.metrics`를 구간 앞뒤로 부름) |
| `crew_join_to_usable` | 멤버 2명, 기록 공개 채널에 메시지 200개가 있는 크루에 초대 링크로 들어와 채널 목록과 그 채널의 마지막 메시지가 보일 때까지(연결은 미리 맺음, 시험에는 DHT가 없음). 들어온 뒤 첫 메시지 전달 시간도 찍음 |

크기는 환경 변수로 바꿉니다: `YANGPA_PERF_MESSAGES`, `YANGPA_PERF_CREWS`, `YANGPA_PERF_CREW_MESSAGES`,
`YANGPA_PERF_FRIEND_MESSAGES`, `YANGPA_PERF_IDLE_SECS`, `YANGPA_PERF_JOIN_HISTORY`. 디버그 빌드처럼 목표를 볼 수 없는
환경에서는 `YANGPA_PERF_REPORT_ONLY=1`로 수치만 찍습니다. 기다릴 때는 조건을 다시 보는 도우미만 쓰고, 고정 시간을 쓰는 곳은
유휴 CPU를 재는 구간 하나뿐입니다.

## 여러 노드 시뮬레이션

`scaled_crew_simulation`(무시, `YANGPA_SIM_NODES`, 기본 24, 3~64)은 한 프로세스에 노드를 띄워 한 크루에 넣습니다.

- 연결: 모두 첫 노드(크루를 만든 노드)와 연결해 그 노드의 초대로 차례로 들어오고, 나머지는 고리로 놓고 양쪽 이웃 둘씩과
  연결·인증합니다(노드마다 피어 5개 안팎, 시험에는 위치 찾기 DHT가 없음). 활성 기기가 8개를 넘으므로 전파는 gossip 경로입니다.
- 놓친 것 채우기: gossip이 놓친 이벤트는 실제처럼 주기 따라잡기가 채웁니다. 다만 간격을 `YANGPA_SIM_SYNC_SECS`(기본 10초,
  실제 기본값은 5분)로 줄이고, 5초 넘게 걸린 전달 수(대부분 gossip이 놓쳐 따라잡기로 받은 것)를 따로 찍습니다.
- 재는 것: 가입마다 걸린 시간(초대 → 멤버·크루 키), 그리고 모든 노드가 하나씩 보낸 메시지가 나머지 모든 노드에 닿는
  시간(받은 노드의 `message.new` 기준, 보낸 노드 자신은 뺌)의 p50·p95·최대와 전체 수렴 시간. 실패 조건은 시간 안에 모두 받는지뿐입니다.
- 지연·손실: 시험 안에서 흉내 내지 않고, CI(`bench.yml`)가 루프백에 `tc netem`(지연 20±5ms, 손실 0.5%)을 건 채 한 번 더
  돌립니다(`YANGPA_SIM_NETEM`에 설명을 넣어 결과 줄에 남김). 루트 권한이 있는 리눅스에서 손으로 돌릴 때도 같습니다:
  `sudo tc qdisc add dev lo root netem delay 20ms 5ms loss 0.5%`, 끝나면 `sudo tc qdisc del dev lo root`.
  측정 환경에는 `tc`가 없고 Docker Desktop의 WSL2 커널에는 `netem`이 없어("Specified qdisc kind is unknown") 지연·손실을
  건 기준선은 아직 없습니다(CI 결과 요약에 남음).
- 실제 Tor 망(대형 크루 12단계): `YANGPA_SIM_TOR=1`이면 노드가 모두 Arti·onion 주소로 돕니다(노드 30~60개). 노드 시작·
  onion 서비스 대기·연결은 동시에 하고, 막 선 onion 서비스는 서술자가 퍼질 때까지 닿지 않으므로 연결은 될 때까지 다시
  겁니다. 기다림은 `YANGPA_TEST_TIMEOUT_SECS`(예: 1800)로 늘립니다. 이어진 쌍마다 `Ping` 세 번의 왕복 절반을 홉 지연으로
  찍고, 그 값을 넣은 하네스 모형 명령(`yangpa-bench scale --gossip N:5 --density 1 --hop-ms 중앙값,p95`)을 함께 찍습니다.
  이때만 크루 토픽 전달 p95 ≤ 3초를 봅니다(`YANGPA_PERF_REPORT_ONLY=1`이면 기록만). 이 컨테이너는 Tor 망에 닿지 않아
  (나가는 TLS가 모두 가로채짐) 측정은 Tor에 닿는 기계에서 돌립니다:
  `YANGPA_SIM_TOR=1 YANGPA_SIM_NODES=40 YANGPA_TEST_TIMEOUT_SECS=1800 cargo test --profile perf -p yangpa-daemon --test perf -- --ignored --nocapture --exact scaled_crew_simulation`.
  모형의 홉 지연에는 Ping이 아니라 고리 이웃 사이 전달(대부분 메시 한 홉, 검증·저장 포함)의 p50·p95를 넣습니다.

루프백 맞춰 보기(디버그 빌드, 4코어 컨테이너, 2026-10-28). 모형은 노드 수 같고 연결 5, 구독 100%:

| 노드 | Ping 절반 p50/p95 | 이웃 전달 p50/p95 | 측정 전달 p50 / p95 | 모형 p50 / p95 |
| ---: | --- | --- | --- | --- |
| 12 | 5 / 9ms | 20 / 34ms | 27 / 41~166ms | 33 / 52~55ms |
| 24 | 8 / 14ms | 61 / 128ms | 103 / 189ms | 123~127 / 191~203ms |
| 32 | 9 / 13ms | 127 / 310ms | 280 / 711ms | 269~277 / 436~442ms |

- 24노드는 20% 안에서 맞고, 32노드 p95는 모형이 38% 낮습니다. 한 프로세스에 노드를 다 띄워 모든 노드가 한꺼번에 보내면 CPU
  줄이 길어져 늦은 홉이 몰리는데, 모형은 홉마다 지연을 따로 뽑기 때문입니다. 실제 Tor에서는 홉 지연이 회로 지연(수백 ms)이라
  이 몫이 작아질 것으로 봅니다(측정으로 확인할 것).
- 실제 Tor 망(2026-10-29, 세영 님 PC Windows, 성능 빌드, 노드 40개 한 프로세스, 최대 상주 메모리 약 1.0GB, 시험 852초):
  전달 1,560건 p50 1,654ms·p95 2,967ms·최대 4,548ms, 5초 넘음 0건, 전체 수렴 4.6초. 목표 p95 ≤ 3초는 겨우 맞습니다(여유 1%).
  가입 p50 3.6초·p95 10.4초·최대 50.5초. 홉: 이웃 전달 p50 494ms·p95 850ms, Ping 왕복 절반 p50 1,082ms·p95 1,812ms·최대 13.7초
  (연결 직후 78쌍을 한꺼번에 재서 회로가 덜 데워진 몫이 섞임). 이웃 전달을 넣은 모형(`--gossip 40:5 --hop-ms 494,850`)은
  p50 1.20~1.25초·p95 1.78~1.85초로 측정보다 p50 35%, p95 65% 낮아 20% 안에 들지 못했습니다. 루프백 32노드처럼 모두가 한꺼번에
  보낼 때 늦은 홉이 몰리는데(같은 회로·같은 CPU), 모형은 홉마다 지연을 따로 뽑습니다. 그래서 모형의 지연 열은 하한으로 읽고,
  45,000노드 표의 p95(1.0~1.2초, 홉 250/1000ms)도 실제로는 더 길 것으로 봅니다. 메시는 섰습니다(모두 닿고 따라잡기로 받은 것
  없음).
- 맞춰 보다가 모형의 메시 규칙을 고쳤습니다: 구독 이웃이 `mesh_n_low`(4)보다 적은 노드를 메시에서 뺐는데, gossipsub 하트비트는
  이웃이 적어도 있는 만큼 붙입니다(libp2p-gossipsub 0.50 `heartbeat`). 고치기 전 모형은 12노드 p95를 450~620ms로 잡았습니다.

| 노드 | 지연·손실 | 전달 p50 | 전달 p95 | 최대 | 5초 넘음 | 전체 수렴 | 가입 p50 / p95 / 최대 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 24 | 없음 | 52ms | 2350ms | 5498ms | 18 / 552 | 5552ms | 95 / 323 / 454ms |
| 32 | 없음 | 193~232ms | 506~681ms | 687~1998ms | 0 / 992 | 710~2234ms(3번) | 156~175 / 386~424 / 448~455ms |
| 50 | 없음 | 495ms | 1291ms | 1521ms | 0 / 2450 | 1546ms | 288 / 554 / 560ms |

지연은 대부분 gossip 메시 밖 노드가 하트비트(1초)마다 오는 IHAVE를 보고 받아 가는 시간입니다. 24노드의 5초 넘은 18건처럼
gossip이 이벤트를 놓치면 따라잡기 전까지 닿지 않으므로, 실제 간격(5분)에서는 그만큼 늦습니다(아래 "빈칸").

이 시뮬레이션이 찾은 문제:

- gossip 검증이 메시지를 처음 올린 피어까지 허용 목록에 있기를 요구했는데, 허용 목록은 이 노드가 인증해 본 기기의 노드뿐이라
  큰 크루에서는 만나지 않은 멤버의 메시지를 버리고 더 전달하지도 않았습니다(첫 노드와 직접 이웃만 받음). 전달한 피어만 허용
  목록에서 보고 내용은 데몬이 검사하도록 고쳤고(decisions.md), 작은 회귀 시험 `gossip_relays_messages_from_unmet_members`
  (무시하지 않음)가 늘 돕니다.
- 고리 이웃이 하나씩뿐일 때(노드마다 피어 3개)는 32노드에서 세 번 중 두 번, 늦게 들어온 노드나 그 이웃이 상태 이벤트·메시지를
  gossip으로 받지 못한 채 따라잡기(당시 5분)까지 멈췄습니다. 새 멤버가 토픽을 구독할 때 아직 그 멤버를 만나지 않은 노드는 비멤버
  점수를 주는데(닫힌 스웜), 그 사이 GRAFT가 거절되면 gossipsub 되물림(기본 60초) 동안 메시에 들지 못하는 것으로 보입니다.
  시뮬레이션은 피어를 늘리고 따라잡기 간격을 줄여 돌고, 원인 정리는 남은 일입니다(아래 "빈칸").

## 규모 시뮬레이션 (`yangpa-bench scale`)

수만 명 크루(대형 크루 확장 설계)를 위해, 네트워크 없이 한 프로세스에서 큰 크루를 재고 아직 만들지 않은 구조를 모형으로
미리 따져 봅니다(`crates/yangpa-bench/src/scale/`, 표 찍기는 `src/scale_report.rs`). 지금 구조가 어디서 막히는지 숫자로
남기고, 바뀐 구조를 같은 표로 비교합니다. 저장·전송 형식은 바꾸지 않습니다.

```text
cargo build --profile perf -p yangpa-bench
# 지금 구조 상태 표만(1000~12000명)
target/perf/yangpa-bench scale
# 전체(4 CPU에서 약 6분)
target/perf/yangpa-bench scale --members 1000,5000,10000,12000 \
  --fanout 4000 --concurrent 1,5 --partition --keys 45053 --days 30 \
  --catchup 1h,1d,1w --gossip 45000:16,32,64 --hop-ms 250,1000 --json scale.json
# 실제 키 트리 대 모형(4 CPU에서 약 15초)
target/perf/yangpa-bench scale --keytree-real 45053,200
# 상태 체크포인트(새 멤버가 받는 양·차가운 시작, 4 CPU에서 3만 명 약 3분, 대부분 키 만들기)
target/perf/yangpa-bench scale --checkpoint 5000,30000
# 실제 데몬 경로로 키 그룹(아래 "키 그룹 데몬 재기")
target/perf/yangpa-bench scale --keytree-daemon 3000
```

| 옵션 | 뜻 |
| --- | --- |
| `--members` | 지금 구조의 상태 표. 아무 옵션 없이 부르면 위 기본값으로 이 표만 찍습니다(MLS 표 `--mls`는 키 갱신 3부에서 openmls와 함께 뺌, 아래 "바꾸기 전 구조"는 그때의 기록). |
| `--fanout K` | 초대 하나를 부모로 둔 가입 기록 K개가 하나씩 도착(동시 가입). |
| `--concurrent 1,5` | `--crew`명(기본 5,000)이 들어오는 동안 그 비율(%)의 가입이 2~8개 앞 이벤트를 부모로 늦게 도착. |
| `--partition` | 두 쪽이 한 시간 동안 따로 받아 준 뒤(한쪽 = 크루의 하루 1%의 1/24, 적어도 10명) 합치기. |
| `--keys N --days D` | 처음 기기 약 N대(사용자 = N/1.5)인 크루의 D일 변동 기록에 키 관리 방식을 돌림(`--schemes legacy,brief,tree`, `--seed`). |
| `--keytree-real N,…` | 실제 키 트리(`yangpa-crypto` keytree)를 크루 기기 N대에서 돌려 같은 작업의 키 트리 모형 값과 나란히 찍음(`--keytree-ban` 밴 물결 기기 수, 기본 1,500). |
| `--keytree-daemon N,…` | 데몬 노드(확정 기기·멤버·가입자)를 로컬 TCP로 띄우고 지어낸 멤버로 크루를 N대까지 채워 탈퇴·가입·밴 물결·전체 재키·기록 나이·직접 인코딩 탈퇴를 실제 데몬 경로로 잼(`--keytree-daemon-ban` 기본 1,500, `--keytree-daemon-days` 기본 365, `--keytree-daemon-direct` 기본 200, `--keytree-daemon-messages` 기본 200). |

  잎은 leaf_master에서 나오므로 그 그룹만 다시 세워서는 옛 확정 기기가 새 경로를 계산하는 것을 막지 못합니다.
  실제 권한에서는 관리자가 모든 채널을 보므로 이는 강등(그리고 관리자 역할 없는 옛 소유자)과 같습니다.

- 목표를 넘은 줄은 가입과 전체 재키 기기당 받기입니다.
- 가입: 이벤트 고정 부분 1,909B(혼합 서명 1,659B)에 Padmé(4 + 본문 252B) = 256B가 붙습니다. 본문이 0B여도 1,913B이고
  2,000B 안에 들려면 본문이 87B 이하여야 하는데, 뿌리 약속·앞 약속(각 32B)과 그룹·순번·앞 이벤트(33B)·`bundle_root`(33B)·
  가입 기기 ID만으로 넘습니다. 검토 전 표(2,101B)는 앞 이벤트를 비워 잰 값이었습니다. 모형도 2,085B로 넘고, 기획서의 2KB는
  서명이 더 작은 이벤트를 가정한 값입니다.
- 전체 재키 기기당 받기 5,708B는 목표를 14% 넘습니다(모형 5,349B도 넘음). 기기 몫마다 `bundle_root` 증명(기기 4만 3천여 개의
  머클 경로 512B)이 붙기 때문이고, 모형은 사용자 조각마다 증명(사용자 2만 9천 명 경로 약 480B)을 한 번 셉니다. 증명은 다른
  멤버가 심은 묶음과 다른 갈래의 묶음을 열기 전에 거르려는 것입니다(decisions.md "키 그룹 초안"). 사용자 조각마다 증명 하나로
  묶으면 약 5,360B가 되지만 확정 기기가 기기 → 사용자 표를 알아야 해 데몬 연결 때 정합니다. 발행 합이 모형보다 31.6% 큰 것도
  같은 증명(43,553 × 약 550B)입니다.
- 감싸기가 56B(모형 80B)라 제거·시간 회전이 작습니다. 밴 물결은 감싸기 하나는 작지만 실제가 감싸기를 더 많이 냅니다.
  실제는 칸을 기기 ID 순으로 채워 한 사용자의 두 기기가 흩어지고, 모형은 한 사용자 기기가 이웃 칸이라 함께 빼면 경로가
  겹치는 것으로 보입니다(추정). 데몬에 연결할 때 같은 사용자 기기를 이웃 칸에 두면 밴·탈퇴가 더 작아집니다.
- 직접 인코딩 가입은 가입자 몫 봉인 상자(약 1.2KB)를 이벤트에 실어 그룹 기기 모두가 받습니다(모형은 가입자에게만 따로).
  256대 이하 그룹에서 Inbox 경로 없이 한 이벤트로 끝내려는 선택이고, 기기당 1.4KB를 더 받습니다.
- 직접 200대 탈퇴는 모형과 바이트까지 같습니다(모형의 X-Wing 봉인 1,227B가 실제 `seal_to` 수신자당 크기). 밴 뒤 160대의
  시간 회전·전체 재키는 +2.1%인데, Padmé 단위(4,096B) 경계 차이입니다.
- CPU: 전체 재키 5.58초는 거의 전부 X-Wing 봉인 43,553개(하나 약 128µs)라 모형 어림(141µs)보다 작습니다. 밴 물결
  47.9ms는 노드 키 생성과 감싸기 13,971개(모형은 대칭 계산을 세지 않음)입니다. 멤버 하나의 적용은 밴 물결에서도 0.3ms 안팎입니다
  (감싸기를 색인 없이 훑음).
- 밴 물결 4,001대는 한 `Rotate`가 조각 하나의 감싸기 한도(17,554개)를 넘어 조각 2개로 나뉩니다. 이 실행에서 멤버가 합친
  갱신을 조각 하나의 목록 한도로 검사해 거부하던 잘못을 찾아, 합친 갱신용 검사(`KeyUpdatePayload::validate_merged`, 지금은
  깊이에서 정한 한도)를 따로 두었습니다.

#### 확정 기기 표 크기 (`--keytree-real 45053`, 키 갱신 검토 반영)

표는 그룹마다 저장 칸·넘기기 요청이 따로입니다(protocol.md "표 저장"). 같은 실행(성능 빌드, 4 CPU)의 마지막 네 줄이고 바이트는
실행마다 같습니다. 상한은 넘기기 요청 하나(메시지 상한 8MiB − 64KiB 여유 = 8,323,072B, 저장 칸 상한 16MiB보다 좁음)입니다.

| --- | ---: | ---: | --- |
| 크루 | 3,104,909B | 45,053 | 깊이 16, 잎은 leaf_master에서 다시 만들어 뺌(검토 때 잰 4.44MiB에서 줄어듦, 기기당 약 69B) |

  가입 2,181B·가입자 4,073B·밴 물결 853,877B·전체 재키 기기당 5,708B까지 모두 같고, 전체 재키 확정 기기 CPU는 9.52초(합치기

- 바퀴는 바뀐 그룹만 씁니다. 가입 하나면 크루 칸 하나(4.5만 대에서 3.1MB)를 다른 칸에 쓰고, 상태가 그대로인 바퀴(상태 이벤트가
  키 그룹과 상관없음)는 표를 꺼내지도 않습니다(`RoundMemo`).

#### 키 그룹 데몬 재기 (`--keytree-daemon 3000`)

위 표는 확정 기기 키 트리 코드만 떼어 돌린 값이고, 이것은 데몬 노드를 띄워 데몬 경로 그대로 잰 값입니다(`scale/keydaemon.rs`,
성능 빌드, 4 CPU, 세 번 145~156초, 그중 크루 채우기 약 30초. 표는 첫 번째). 노드는 확정 기기 A(소유자), 실제 멤버 B, 재는 때마다 새로 드는 실제
가입자(c, 기록 나이 30·90·180·365일째 가입자)이고 로컬 TCP로 잇습니다(Tor 없음, `NodeConfig::for_test`: 묶음 창 50ms,
`key_handover_wait` 2초). 크루 기기 3,000대 = 2대 사용자 566명 + 밴 물결 사용자 30명 × 50대 + 1대 사용자 366명(탈퇴 1명과
기록 나이 날마다 1명) + A·B, 사용자 964명, 트리 깊이 12. 지어낸 멤버(`testkit::synthetic_members`)의 상자 키는 아무도 열 수
없는 값이라 받는 쪽 바이트는 A가 저장한 이벤트의 전송 크기로 셉니다. 바이트는 실행마다 거의 같고(탈퇴는 칸 배치에 따라
3,358~3,422B), 벽시계는 같은 기계의 다른 작업에 따라 움직입니다.

평상시(메시지 200개를 A·B가 반씩) 키 묶음(`KeyShare`) 0개, 작업마다 불변식 검사 105번 중 어긋남 0번(빚 없음·전체 재키 요구

- 가입·전체 재키 기기당 받기가 목표를 넘는 까닭은 위 "실제 키 트리 대 모형"과 같습니다(가입은 이벤트 고정 부분 1,909B,
  전체 재키는 기기 몫마다 `bundle_root` 증명, 여기서는 12칸 384B).
- 가입 시간: 3,000대 크루의 공간 스트림은 수락 응답 한도에 다 실리지 않아 `Pending`으로 답하고 가입자가 따라잡습니다. 크루 키를
  얻기까지 6.0초(세 번 5.8~6.9초)에는 따라잡기 첫 간격(1초)과 옛 상태 키 묻기 전 지연(1초, `GetStateKeys`)이 들어 있습니다. Tor에서는 왕복마다
  더 붙습니다.
- 밴 물결은 위 실제 키 트리 줄(사용자 996명·1,500대, 크루 45,053대)과 구성이 달라 바로 비교할 수 없습니다. 여기서는 50대씩인
  사용자 30명이라 빠지는 기기가 트리의 이웃 칸에 모여 감싸기가 적습니다.
- 전체 재키 조각 블롭은 64KiB 조각(`shards::PAGE`)으로 나뉩니다. 위 표를 잴 때는 기기 하나가 자기 사용자 몫(평균 3.3KB)을
  얻으려고 색인 조각과 자료 조각 하나씩(약 131KB)을 내려받았습니다. 지금은 `GetKeyShard`로 자기 기기 몫만 묻고(약 2KB, 아래
  검토 반영 뒤 값), 조각 단위 받기는 그 답을 얻지 못했을 때만입니다.
- 가입 묶음은 90일째부터 8,354B로 멈춥니다(상태 키 64개까지 + 크루 R + 트리 몫). 예전처럼 상태 키 전부를 묶었다면 365일 뒤
  마지막 가입자가 가진 423개로 약 24KB였습니다. 그보다 오래된 키는 가입자가 멤버에게 물어 받았습니다(`GetStateKeys`).
- 키 갱신 검토 반영 뒤 다시 잰 값(같은 명령, 성능 빌드, 155.95초, 채우기 31.24초): 밴 물결은 바퀴를 미루는 시험 손잡이
  (`hold_commits`) 없이 API로 잇달아 30명을 밴해도 묶음 창이 크루 갱신 1개·1조각으로 묶습니다(61,280B, 확정 기기 벽시계
  228ms는 묶음 창 포함. 예전에는 밴마다 창을 건너뛰어 갱신이 밴 수만큼 났음). 전체 재키에서 실제 멤버 B가 받는 바이트는
  머리 이벤트 2,174B + `GetKeyShard` 답 2,058B = 4,232B로 기기당 5KB 목표 안입니다(예전 블롭 조각 단위 133,246B). 답은 요청
  기기의 몫만이라 기기 2대 사용자도 같은 크기입니다(사용자 몫 평균 3,332B를 다 받으면 5,506B). 나머지 줄은 위 표와 같거나
  칸 배치에 따른 차이입니다(탈퇴 3,358B, 가입 묶음 처음 5,538B, 불변식 어긋남 0번).
- 이 재기에서 데몬 결함 둘을 찾아 고쳤습니다(decisions.md "키 갱신 3부"의 "고친 것"): 머리가 16개를 넘을 때 크루 갱신 부모
  고르기, gossip이 지금 상태로 거부한 이벤트의 빈 부모 채우기. 둘째는 고치기 전 실행이 크루 키를 기다리며 약 600초(멤버가
  주기 따라잡기 전까지) 멈췄습니다. 고친 뒤 세 번 돌려 15초 넘게 기다린 단계가 없었습니다.
- 상태 체크포인트와 합친 뒤(같은 명령, 126.9초, 채우기 32.6초): 바이트는 탈퇴 3,422B, 가입 2,158B, 밴 물결 61,280B, 실제
  멤버 B의 전체 재키 4,216B로 위와 같거나 칸 배치 차이이고, 불변식 105번 중 어긋남 0번입니다. 가입 응답은 `Joined` 2.6초, 크루
  키를 얻기까지 2.6초(위 `Pending` 2.0초, 6.0초)입니다. 크루가 256대를 넘으면 첫 체크포인트가 생겨 가입자는 공간 스트림 전체
  대신 체크포인트·스냅숏과 경계 위 이벤트를 받습니다.
  가입 묶음은 처음 5,282B, 30일 7,074B, 90일 8,354B, 180·365일 8,866B입니다(위 8,354B보다 바탕의 유효 키 몇 개만큼 큼).
  처음에는 체크포인트 크루 머리 뒤 키를 1,024개까지 다 실어 365일 뒤 16,546B(목표 16KB 넘음)였습니다: 이 재기는 하루를
  기다리지 않고 당겨 돌려 체크포인트의 24시간 주기가 오지 않고, 쉴 틈(`settle`)이 가입을 기다리는 동안에만 생겨
  체크포인트가 90·180·365일 가입 때만 나와 머리 뒤 키가 235개까지 쌓였습니다. 머리 뒤 키도 최근 64개만 싣고 나머지는
  체크포인트 없을 때처럼 `GetStateKeys`로 묻게 해 묶음이 체크포인트 주기와 상관없게 했습니다(decisions.md "체크포인트와 키
  그룹 합치기"). 확정 기기 벽시계는 탈퇴 70ms(위 30.7ms는 검토 반영 전 값으로, 그 뒤 단건 추방도 묶음 창 50ms를 기다림)·밴

- "구독 이웃"은 구독자 하나의 구독한 이웃 수 평균, "P(메시)"는 구독 이웃이 mesh_n_low(4) 이상인 구독자 비율입니다. 모형의
  메시는 이웃이 4보다 적어도 있는 만큼 붙습니다(하트비트와 같음, 12단계 루프백 측정으로 고침). "소문만"은 IHAVE/IWANT로만 받은 비율, "직접 받음"은 작성자가 NoPeers로 모든
  기기에 직접 보내 받은 비율, "올림"은 글 하나에 작성자가 보내는 사본 수(flood 켬/끔)입니다. p50·p95가 "못 닿음"이면 그
  분위까지 닿지 않은 것입니다.
- 무작위 연결에서 구독자가 적은 토픽(f ≤ 5%)은 구독 이웃 평균(k·f)이 4보다 적습니다. 작성자에게 구독 이웃이 하나도
  없으면 NoPeers로 모든 기기에 직접 보내 닿지만, 하나둘 있으면 NoPeers가 나지 않고 그 작은 덩어리에만 닿습니다. 그래서
  k가 커질수록 전체 도달이 오히려 떨어집니다(f 1%: k 16 → 75%, k 64 → 61%). 못 닿은 구독자는 따라잡기까지 늦습니다.
- 구독 이웃이 1~3개인 칸(k 32·f 5%, k 64·f 5%)은 이웃이 적어도 메시가 붙어 길게 이어지므로(대부분 5홉 넘음) k 64·f 5%는
  95% 닿고 p50 1.6초·p95 5.1초, k 32·f 5%는 큰 덩어리가 63%라 61%만 닿습니다(12단계에서 모형 메시 규칙을 고치기 전에는
  소문으로만 번진다고 보아 p50 3~24초).
- 토픽 인지 연결이면 모든 칸에서 메시가 생기고 p95가 0.5~1.2초입니다. f 100%는 연결 방식과 무관하게 p50 0.8~1.0초,
  p95 1.0~1.2초(대부분 5홉 이상)입니다.
- flood를 끄면 작성자 올림이 k에서 약 7(메시 피어)로 줄어듭니다. 도달·지연 열은 flood를 켠 경우입니다. NoPeers 직접
  보내기는 flood와 무관합니다.

  사본 처음 25.2ms(기기 목록 12.1, 채널 둘 12.9, 기기 → 사용자 0.3: 앞 사본의 표에서 바뀐 멤버만 고침). 멤버 표와 기기 표를
  나란히 걷고 쥔 항목으로 권한을 계산하기 전에는(사용자마다 B-트리 찾기 세 번과 역할 목록 복사) 135.7ms / 109.0ms였습니다.
- 처음 읽기는 새 프로세스에서 `Store::open`부터 상태 행 읽기(멤버 30,000명, 기기 44,992대를 다시 지음), 색인 첫 계산까지입니다.
  기기 키 4,096개(LRU 크기)를 DB에서 처음 찾는 데 289ms(키 하나에 약 70µs: 행마다 페이지 복호화와 약속 다시 계산)라,
  4.5만 대 모두에 봉인하는 일이 생기면 처음 한 번 약 3초가 듭니다(지금은 그런 경로가 없음).
- 데몬 시작: `spaces::load_all`은 저장된 상태 행을 바뀐 행만 쓰는 기준으로만 쓰고, 상태는 저장된 공간 스트림 이벤트를 다시
  확인·해소해 짓습니다. 가입 하나를 다시 볼 때 이벤트 서명 확인 92µs + 기기 목록 서명 확인 247µs(신원 서명 + 공동 서명)라
  3만 명이면 이것만 10.2초이고, 초대 증명·프로필·KeyPackage 확인, 복호화, 해소가 더해집니다(위 "해소기 시나리오"의 4,000명
  한꺼번에 넣기 1.3초에서 가입 하나에 약 0.3ms). 남의 지난 판 기기 목록은 서명을 보기 전에 거르게 해(`accept_device_list`) 판마다
  세 번째로 하던 목록 확인은 없앴습니다. 저장된 이벤트 가운데는 해소기가 거부한 것도 있어 확인 없이 믿을 수 없으므로, 저장된
  상태에서 바로 시작하지 않습니다. 체크포인트가 생긴 뒤에는 받아들인 바탕의 스냅숏(소유자가 서명한 상태 해시로 확인)과
  경계 위 이벤트만 다시 넣어 시작합니다(`checkpoint::restore`, 아래 "상태 체크포인트": 3만 명 0.57초).
- 해소기 메모리: 가입·기기 목록 갱신 본문(14KB 남짓)을 들고 있지 않고 넣을 때 확인한 결과와 간추린 기록만 남깁니다
  (decisions.md "해소기가 들고 있는 이벤트"). `scale --fanout 4000`(4,000명 동시 가입, 같은 기계·다른 때)에서 해소기 RSS 증가가
  73MB → 12MB, 최대 RSS 355MB → 175MB입니다. 같은 일로 상태 기록의 목록 해시를 빼고 키 약속을 넣을 때 한 번만 세게 되어
  `scale --members 10000 --mls 64`의 1만 명 다시 해소가 184.8ms → 63.9ms, 동시 가입 해소 171.7ms → 75.7ms, 옛 부모 3% 하나씩이
  3.0초(비증분 평균 6.1ms) → 1.6초(2.0ms)가 됐습니다(바꾸기 앞 99f5459와 같은 기계에서 차례로, 앞의 것은 부하 평균 3~7).
- gossip 허용 목록: 상태를 적용할 때와 멤버 피어를 인증할 때마다 활성 기기마다 노드 기록을 DB에서 찾던 것(4.5만 대에
  102~117ms)을 아는 노드 한 번 훑기로 바꿨습니다(`sync_service::member_peers`, 쿼리 한 번 + 아는 노드 수만큼).
- 상태 체크포인트와 합친 뒤 같은 명령: 바이트(행·값·WAL, DB 192.5MB)와 상주 메모리(77~78MB)는 같고, 시간은 위 표보다
  1.3~2.5배였습니다(적용 CPU 중앙값 0.35~0.67ms·최대 3.74ms, 색인 첫 계산 136.7ms, 처음 읽기 0.33초, 짓기 441ms, 처음 통째로
  쓰기 5.2초). 같은 때 합치기 전 키 쪽 트리(e0db336)를 같은 설정으로 지어 번갈아 두 번씩 돌리면 같은 범위라(적용 CPU 중앙값
  키 쪽 0.44~0.80ms 대 합친 쪽 0.39~0.75ms, 색인 첫 계산 145.4·145.6ms 대 149.3·126.2ms, 처음 읽기 0.40·0.37초 대
  0.39·0.36초) 코드가 아니라 그날 기계 몫입니다(바뀌지 않은 서명 확인도 실행마다 가입 하나 100~197µs). 목표 판정은 그대로입니다.

#### 가입 키 묶음과 받은편지함 (멤버 30,000명)

`yangpa-bench scale --join-inbox 1,64,1024,9000 --join-members 30000`. 가입자 기기 2대, 키 64개씩, 하루 가입은 멤버의 1%(300명).
바이트는 전송 크기(postcard)입니다.

| 묶음 키 | 묶음 이벤트 | 가입 기록 | 묶음(예전/지금) | 다른 멤버 1명·가입 1회 예전 → 지금 | 다른 멤버 1명·하루 예전 → 지금 | 크루 전체·가입 1회 예전 → 지금 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 12.8KB | 4.3KB / 4.4KB | 17.1KB → 12.8KB | 5.02MB → 3.76MB | 502.08MB → 376.20MB |
| 64 | 1 | 12.8KB | 5.6KB / 5.7KB | 18.4KB → 12.8KB | 5.40MB → 3.76MB | 540.33MB → 376.20MB |
| 1024 | 16 | 12.8KB | 87.4KB / 88.9KB | 100.2KB → 12.8KB | 29.36MB → 3.76MB | 2936.47MB → 376.28MB |
| 9000 | 141 | 12.8KB | 763.8KB / 777.6KB | 776.7KB → 12.8KB | 227.54MB → 3.76MB | 22754.12MB → 376.96MB |

- 묶음에는 상태 키 전부와 과거 기록 공개 채널의 기록 키가 듭니다. 상태 키는 확정 기기가 기기를 뺄 때마다(추방·탈퇴·기기 폐기
  묶음) 새로 나오므로 크루가 오래될수록 늘어납니다. 하루 탈퇴가 멤버의 1%인 3만 명 크루가 빼기마다 회전하면 30일 뒤 약 9,000개
  (위 마지막 줄, 상한), 확정 기기가 빼기를 묶어 회전하면 그보다 적습니다.
- 가입자가 아닌 멤버는 이제 가입 기록만 받습니다. 키가 1개여도 가입 한 번에 4.3KB(봉인 2개 + 혼합 서명)를 덜 받고, 9,000개면
  가입 한 번에 764KB, 하루 224MB를 덜 받습니다. 가입자는 범위·기준점(이벤트마다 약 100B)만큼 조금 더 받습니다.
- 위 표는 키 그룹으로 바꾸기 전에 잰 것이라 묶음에 상태 키 전부와 기록 키가 들었습니다. 키 갱신 2·3부 뒤 가입자 묶음은 최근
  상태 키 64개 + 크루 R + (트리면) 자기 몫 묶음이고 그보다 오래된 상태 키는 가입자가 멤버에게 묻습니다(`GetStateKeys`). 그때
  공간 스트림에 실리던 MLS 추가 커밋·웰컴(그룹 기기당 약 1.4KB)은 크루 가입 전진 갱신 하나로 바뀌어, 다른 멤버가 가입 한 번에
  받는 키 바이트는 2KB 안팎입니다(위 "키 그룹 데몬 재기").

#### 상태 체크포인트 (멤버 5,000명·30,000명, 꼬리 500)

`target/perf/yangpa-bench scale --checkpoint 5000`과 `--checkpoint 30000`(따로, 부하 평균 4~5). 소유자 기기가 가입 N개를
차례로 받아 준 선형 기록(시작·초대 + 가입 N개) 끝에 체크포인트를 내고, 그 뒤 가입 500개(다음 체크포인트 문턱인 상태 이벤트
1,000개의 절반)가 이어진 때입니다. 새 멤버는 체크포인트 이벤트, 스냅숏 블롭, 경계 F 이상 이벤트(경계 위 조상 33개 + 꼬리)를
받습니다. 바이트는 전송 크기(postcard), MB는 MiB. 처음 잴 때는 해소기 멤버 상한이 1만 명이라 시험에서만 넓혔고, 지금은 기본 상한(`MAX_MEMBERS` 65,536) 안입니다.

| --- | --- | --- |
| 3만 명 크루 새 멤버 내려받기 20MB 이하 | 16.6MB(스냅숏 9.9MB + 꼬리 6.7MB + 체크포인트 9.8KB), 전체 기록 382.5MB의 4.3% | 맞음(꼬리가 문턱까지 다 차면 아래) |

| 데몬 시작 1초 이하(앞 "상태 저장·색인") | 스냅숏에서 0.57초, 처음부터 20.9초 | 해소기 몫은 맞음 |

- 스냅숏은 멤버 하나에 약 350B입니다(간추린 기기 기록은 키 약속만 싣고 기기 키는 `GetDeviceKeys`로 따로 받음). 키 그룹과
  합친 뒤에는 크루 키 사슬 상태가 들어가 약 410B입니다(아래 "키 그룹과 합친 뒤"). 상한 32MiB에는 관리 설정이 작으면 약
  8만 명(합치기 전 9.5만 명), 한도까지 채우면(아래 "해소기 스냅숏"의 11MB) 약 5.5만 명(합치기 전 6.5만 명 남짓)에서 닿습니다.
  블롭은 평문보다 조각마다의 인증 태그만큼 큽니다(결정론적 암호화, 압축 없음).
- 새 멤버 몫의 40%가 꼬리(가입 기록 약 13KB × 500)입니다. 체크포인트는 상태 이벤트 1,000개마다라 꼬리가 문턱까지 다 찬
  때 가입만이면 약 13.4MB가 되어 3만 명에서 합계 약 23MB입니다. 하루 가입이 멤버의 1%(300명)면 문턱보다 24시간 주기에 먼저
  닿아 꼬리는 그보다 짧습니다.
- 해소기는 같은 `prev`의 겨룬 체크포인트를 판정하려고 지금 바탕의 앞 바탕까지 남기므로, 첫 체크포인트로는 항목이 줄지 않고
  다음 체크포인트에서 앞 바탕 앞이 빠집니다(항목은 많아야 체크포인트 두 주기 남짓 + 경계 위 조상). "다음 체크포인트 넣기"는
  받는 노드마다 하는 일(상태 해시를 다시 계산하는 정규 인코딩·머클 트리 + 앞 기록 버리기)이고, 데몬은 이견 판정을 위해 스냅숏
  암호화(26ms)를 더 합니다. 초안은 쓰는 기기만 만듭니다.
- 겨룬 체크포인트(같은 바탕을 잇는 맞는 후보 둘 이상)는 후보마다 뒤 구간을 미리 해소해 봅니다(갈림마다 후보 4개까지라 많아야 그
  구간 해소의 4배). 지금 바탕을 잇지 않는 체크포인트가 오면 창의 바탕부터 다시 해소합니다(항목 많아야 두 주기 남짓, 위 "다음
  체크포인트 넣기"와 같은 규모). 둘 다 서명이 맞는 체크포인트가 있어야 하므로 소유자 기기가 갈라졌을 때만 생깁니다. 바탕이
  바뀌거나 앞 구간을 버릴 때 머리·빠진 부모를 다시 세는 것은 항목 수에 비례(수백 개)라 따로 재지 않았습니다.
- 스냅숏은 떠난 사람의 기기 기록(사람마다 약 250B), 지운 초대의 토큰 해시(32B), 지운 채널·역할 ID(16B)를 정리하지 않습니다
  (나중 판정에 쓰임, decisions.md "스냅숏 정리"). 상한 32MiB에는 활성 3만 명에 떠난 사람 약 9만 명이 쌓여야 닿고, 닿으면
  쓰는 기기는 초안만 만들고 암호화하지 않은 채 그만두며(확인 간격마다 초안 하나, 9.9MB에 258ms인 위 값으로 어림하면 약 0.8초), 새 멤버는 처음부터 받습니다.
- 처음부터 차가운 시작의 상주 메모리는 디코딩한 이벤트(가입 본문)를 한꺼번에 들고 해소하는 몫과 해제했지만 할당기가 돌려주지
  않은 몫을 포함합니다. 스냅숏에서는 해소기가 아는 항목이 534개라 크루 크기와 상관없이 작고, 상태 자체(3만 명)가 대부분입니다.
- 읽기는 파일에서입니다. 데몬은 SQLCipher에서 체크포인트 이벤트·스냅숏 블롭·경계 위 이벤트(`events_by_lane_from`)를 읽으므로
  앞 "상태 저장·색인"의 열기·읽기 비용이 더해집니다.
- 받는 양에는 새 멤버의 키 묶음(받은편지함, 위)과 채널 기록이 없습니다. 기기 키는 필요한 기기만 `GetDeviceKeys`(한 번에
  512대)로 받고, 확정 기기는 봉인할 대상 키를 미리 받아 둡니다.
- 멤버 프로필·뱃지 카드도 이 표에 없습니다. 들어온 뒤 뒤에서 `GetMemberCards`(한 번에 128명)로 받으며, 서명 프로필을 사람마다
  약 1KB로 어림하면 3만 명 크루에서 약 30MB입니다(재지 않은 값, 가입을 막지 않음).

#### 키 그룹과 합친 뒤 (상태 체크포인트 + 키 갱신 1~3부)

두 갈래를 합친 트리에서 같은 명령을 성능 빌드, 4 CPU로 다시 돌렸습니다(`--checkpoint 5000,30000`은 한 번에, 3만 명·5천 명은
한 번씩 더). 괄호는 위 표(합치기 전)입니다.

- 가입 기록에 MLS KeyPackage가 없어(약 13.1KB → 9.4KB) 전체 기록과 꼬리가 약 25% 줄었습니다.
- 스냅숏은 멤버 하나에 약 64B 커졌습니다(+19%). 정규 인코딩에 크루 키 사슬 상태(`CrewKeys`)가 들어가서입니다(decisions.md
  "체크포인트와 키 그룹 합치기"). 이 재기는 확정 기기가 키 갱신을 내지 않아 활성 기기 모두가 가입 대기 기록(`added_by`: 기기 ID +
  이벤트 ID = 64B)으로 남고, 실제 크루에서는 같은 기기가 사슬 멤버(`members` 32B + `joined_at` 약 33B)라 크기가 같습니다. 꼬리가
  준 만큼 상쇄되어 3만 명 새 멤버 받는 양은 +1%(20MB 목표 안)입니다.
- 이 기계는 같은 바이너리도 실행마다 크게 흔들려(바뀌지 않은 초안이 257ms → 383ms) 합치기 전 체크포인트 트리(5e9f446)를
  같은 설정으로 지어 번갈아 돌려 견줬습니다(3만 명 세 번씩, 5천 명 두 번씩). 3만 명에서 다음 체크포인트 넣기는 평균 274ms →
  360ms(+31%), 초안 286 → 311ms(+9%), 스냅숏에서 차가운 시작 0.62 → 0.66초(+5%)이고, 5천 명은 넣기 46 → 51ms, 차가운 시작
  0.38 → 0.43초입니다. 넣기를 나눠 재면(한 번, 303ms 대 362ms) 늘어난 59ms는 상태 해시를 다시 계산하는 다이제스트 +37ms(정규
  인코딩 10.6MB → 12.6MB, 흔들림 포함), 앞 기록 버리기·DAG 다시 세기 +13ms(항목 3만 개 해제), 크루 키 정리(`CrewKeys::seal`이 가입 기록
  3만 개를 훑음) +3.5ms, 나머지 다시 해소 +5ms입니다. 넣기는 체크포인트마다(상태 이벤트 1,000개나 24시간) 한 번이라, 크루 키
  상태를 정규 인코딩에 넣은 값(decisions.md "체크포인트와 키 그룹 합치기"의 정규 인코딩)으로 받아들였습니다.

### 해소기 스냅숏

이어 붙일 수 없는 삽입(동시 이벤트, 빈 구간 채움, 본문을 받은 순서 연결)을 예전에는 늘 처음부터 다시 해소했습니다. 이제
해소기는 처리 순서와 스냅숏을 남겨 두고, 새 항목이 영향을 줄 수 있는 가장 이른 위치 앞의 스냅숏에서 나머지만 다시 해소합니다
(protocol.md "상태 해소 순서", 결과가 처음부터 해소한 것과 같은지는 `state::tests`의 `incremental_equals_scratch`가 봄).
그 위치가 기록 끝이면(동시 갈래를 그 갈래의 마지막 이벤트 뒤로 이어 감) 스냅숏으로 돌아가지 않고 새 항목만 처리합니다.

- 측정은 `scale` 표의 마지막 열(`scale::stale_chain`)입니다. 소유자가 N명을 차례로 넣는 선형 가입 기록에서 3%는 머리 대신
  2~9개 앞의 옛 이벤트를 부모로 고르고(동시 이벤트) 다음 기록이 머리를 모두 덮어 합칩니다. 하나씩 넣으며 전체 시간, 이어 붙이지
  못한 삽입의 수와 평균 시간, 처음부터 해소한 횟수, 스냅숏 재생 횟수와 평균 재생 길이를 셉니다. 기기 목록은 신원 서명만 하고,
  해소기 멤버 상한은 N+1명으로 넓힙니다(`Limits`).
- 스냅숏은 처리 1024항목마다 남기고 16개를 넘으면 끝에서 멀수록 성기게 솎습니다. 끝에서 d만큼 앞부터 다시 해소할 때 재생
  길이는 처리 기록 약 90만 항목까지 2(d + 1024) 안, 300만 항목까지 2.2(d + 1024) 안입니다(실제 상수로 솎는 시험
  `snapshot_bound_with_release_constants`; 같은 규칙으로 1000만 항목이면 2.5배, 3000만이면 3배). 1024항목보다 짧은 기록에서는
  돌아갈 스냅숏이 없어 처음부터 해소합니다(1000명 행).
- Machine 복제: 3만 명 합성 상태(`state::machine::synthetic`, 기기 4.5만 대, 밴 1천, 떠난 사용자 3천, 커밋 2천)를
  `cargo test --profile perf -p yangpa-sync machine_clone_cost -- --ignored --nocapture`로 잽니다. `BTreeMap` 그대로면 53ms,
  멤버·기기 목록만 `Arc`로 들면 10ms(기기 주인·멤버가 된 시각·쓴 초대 증명 같은 내부 표를 여전히 다 복사)라, 멤버 수만큼
  커지는 표를 모두 지속 맵(`model::SharedMap` = `imbl::OrdMap`, 마디 16항목)으로 바꿨습니다. 복제는 0.15µs이고, 비용은
  복제 뒤 처음 고치는 경로의 마디 복사로 옮겨 갑니다(복제 뒤 멤버 1024명을 고치면 4.6ms, 혼자 가진 뒤 같은 쓰기는 0.7ms).
  멤버·기기 목록 값을 `Arc`로 드는 것은 이 마디 복사가 값(기기 목록은 상자 키 1.2KB)까지 복사하지 않게 하려는 것입니다.
- 관리 설정도 한도까지 채우면 큽니다: 같은 시험의 `synthetic::fill_admin_config`(역할 250개와 그 표시 범위, 채널 500개에
  덮어쓰기 100개·주제 1024자·포럼 태그 20개, 초대 1000개에 역할 250개씩, 이모지 500개, 채널별 작은 표)는 직렬화 11MB입니다.
  그래서 채널·역할 표시는 `SharedMap`, 초대는 `imbl::Vector`, 해소기 안의 지운 채널·역할 ID(지울 때마다 늘기만 함)와
  복구 전달도 지속 자료 구조로 둡니다. 이 상태의 복제는 66µs이고, 스냅숏마다 따로 복사되는 나머지 작은 표(역할, 이모지,
  보관 노드, 채널별 전송 방식·익명·대문 글·첨부 한도·수정 금지, 크루 서버, 전환 전 채널과 기록 공개 동의)는 직렬화
  231KB입니다(보통 크루는 수 KB).
- 메모리: 스냅숏은 서로, 또 현재 상태와 큰 표의 마디를 나눠 가집니다. 스냅숏 하나가 따로 드는 메모리는 그 뒤에 고친 경로의
  마디(쓰기마다 깊이 3~4개)와 위의 작은 표 사본이므로, 크루 하나의 스냅숏 16개는 작은 표로 많아야 16 × 231KB(직렬화 기준,
  메모리에서는 그 두세 배)에 고친 경로를 더한 만큼입니다.

`scale --members 1000,10000 --mls 64`를 기준(4de470c)과 바꾼 뒤(1a2fc20)를 번갈아 세 번씩 돌린 범위(같은 기계, 다른 작업이
함께 돌아 부하 2.6~3.0). 기준에는 옛 부모 측정 함수가 없어, 그 세 줄의 기준은 앞서 같은 함수를 기준에 붙여 잰 값입니다.

## 휘발성 세션 키 회전

참가자가 n명(기기)인 휘발성 채널에서 세대 하나를 내는 데 드는 바이트입니다. 예전에는 세대마다 새 키를 참가자 모두에게
봉인한 키 묶음 하나(약 n × 1.24KB)를 참가자 n명에게 똑같이 보내, 입장·퇴장 한 번에 n² × 1.24KB가 오갔습니다(200명이면 약
50MB). 이제 회전 공지(키 없음)와 기기 하나 앞 감싸기로 나눕니다(protocol.md "휘발성 채널").

| 바뀜 | 담당이 보내는 것 | n = 200 |
|---|---|---|
| 가입(누가 들어옴) | 공지 n개(약 1.1KB: 본문 113B + 헤더 + 짧은 서명 730B) + 가입자 감싸기 1,303B | 약 0.22MB |
| 나감·추방(1초에 한 번으로 묶음) | 공지 n개 + 감싸기 n개 | 약 0.48MB |

감싸기·공지 본문 크기는 `volatile::tests::rotation_wire_sizes_stay_small`이 잽니다(감싸기 1,303B, 더한·뺀 기기 하나인 본문
113B). 공지는 채널 이벤트라 짧은 서명(730B)입니다(9단계 전에는 긴 서명 1,659B로 공지 약 2KB, 가입 0.4MB·나감
0.66MB). 상시 참여 채널은 참가 상한(기본 200, 2..=2000)이 나감 한
번의 감싸기 수를 묶습니다.

## 명령 수 회귀 검사 (`crates/yangpa-bench`)

기획서의 "러스트 벤치마크(암호화, 이벤트 저장, 동기화 비교)를 CI에서 돌려, 기준선보다 느려지면 빌드를 실패"를 벽시계 시간
대신 **명령 수**로 합니다. 공유 러너의 벽시계 시간은 흔들림이 수십 %라 문턱을 둘 수 없지만, valgrind cachegrind의 명령 수는
같은 바이너리면 거의 같습니다(아래 두 번 잰 차이 0~1%).

- 작업마다 준비(`setup`)와 반복(`run(n)`)을 나누고, 반복 수만 다른 두 실행(`n1 = 2`, `n2 = 10`)의 명령 수 차이를 8로 나눠
  한 번당 값을 냅니다. cachegrind는 반복 부분만 셉니다(`--instr-at-start=no`, `run`이 반복 앞뒤로 클라이언트 요청
  `CACHEGRIND_START/STOP_INSTRUMENTATION`을 냄). 준비를 함께 세면 이벤트를 서명해 두는 준비의 명령 수가 FN-DSA의 무작위
  거절 표본 추출 때문에 실행마다 수백만씩 달라 두 실행의 차이에 섞였습니다(같은 바이너리로 `store_fingerprints_5k`가
  462만~911만, 2026-10-30에 고침). 반복 안에서 무작위 키·nonce를 쓰는 곳이 있어 완전히 같지는 않습니다.
- 저장소를 읽는 작업은 준비 끝에 몇 번 돌려 읽기 연결(기본 3개, 연결마다 페이지·문장 캐시가 따로)을 데워 둡니다.
- 빌드는 `[profile.perf]`(release에서 LTO를 끄고 codegen-units 16, 패닉 풀기). CI 빌드 시간을 줄이기 위함이며 시험 바이너리도
  이 프로필로 만듭니다.
- 허용치는 작업마다(`Spec::tolerance`, 암호·지문 비교 5%, MLS·저장·적용 10%). `gate --threshold`를 주면 모든 작업에 그 값.
- 명령 수는 컴파일러 판에 따라 달라집니다. 그래서 PR은 **기준 커밋을 같은 환경·같은 툴체인으로 다시 재서** 비교합니다
  (`scripts/bench-gate.sh <기준 커밋>`). PR CI에서는 돌리지 않으므로(GitHub 서버 러너가 막혀 있고 PC 러너는 Windows)
  개발 환경(리눅스, `RUSTUP_TOOLCHAIN=<기준선 툴체인> YANGPA_BENCH_STRICT=1`)에서 재고 결과를 PR에 적습니다.
  기준 커밋에 이 크레이트가 없거나 main에 올라간 뒤·주간 실행에서는 저장된 기준선(`crates/yangpa-bench/baseline.json`)과 비교합니다. 여러 PR에 걸쳐 조금씩 쌓인 회귀는 이 비교가 잡습니다.
- 그 비교가 늘 같은 조건이 되도록 `bench.yml`의 검사 작업은 러너 이미지(`ubuntu-24.04`)와 툴체인(`BENCH_TOOLCHAIN`, 기준선의
  `toolchain`과 같은 판)을 고정하고 엄격 모드(`YANGPA_BENCH_STRICT=1` → `gate --strict`)로 돕니다. 툴체인이 기준선과 다르면
  참고용으로 넘기지 않고 실패하므로, 고정 판을 올릴 때는 기준선도 같이 다시 잽니다(`yangpa-bench` 시험
  `ci_toolchain_matches_baseline`이 둘을 맞춰 봄). 손으로 돌릴 때(`YANGPA_BENCH_STRICT` 없음)는 툴체인이 다르면 참고용입니다.
- 기준선 갱신: CI 산출물 `bench-instructions`의 `head.json`을 `baseline.json`으로 복사하거나, 같은 툴체인으로 손으로
  `cargo build --profile perf -p yangpa-bench && target/perf/yangpa-bench measure --toolchain "$(rustc --version)" --out crates/yangpa-bench/baseline.json`.

위 숫자는 준비를 빼고 센 뒤(2026-10-30) 다시 잰 기준선입니다. 그 전 값(`store_insert_100` 42,568,905, `ingest_batch_20`
109,010,432, `store_fingerprints_5k` 6,777,221 등)은 준비의 흔들림이 섞인 값이라 직접 비교하지 않습니다.

양자 내성 전환(봉인 상자 X-Wing, MLS ML-KEM 스위트, Ed25519 + FN-DSA-512 혼합 서명)으로 `sealed_box_8`·`mls_commit_8`(키 갱신 3부에서 MLS와 함께 뺀 작업)이 약 2배,
`event_sign_verify`가 약 6배(대부분 FN-DSA 서명, 검증은 가벼움), 서명이 64바이트 → 1659바이트라 `store_insert_100`이 약 1.8배가 됐습니다.
받는 쪽 경로(`ingest_batch_20`)는 검증만 하므로 약 1.2배입니다.

벽시계 시간은 `yangpa-bench time [작업…]` 또는 `cargo bench -p yangpa-bench`로 봅니다(사람이 보는 숫자, 검사에는 쓰지 않음).
명령 수는 `yangpa-bench measure [작업…]`(valgrind 필요)로, 한 작업만 손으로 돌릴 때는 `yangpa-bench run <작업> <n>`.

## 측정 환경

- 리눅스 x86_64: Windows PC의 Docker Desktop(WSL2 커널 5.15)에서 띄운 `ubuntu:24.04` 컨테이너, Intel Core i7-13700KF
  24스레드(AVX2), 메모리 15GiB. `rustc 1.97.0`, `[profile.perf]`. 벽시계 열은 이 컨테이너에서 `yangpa-bench time`으로 잰 값.
- valgrind 3.22(cachegrind, `--cache-sim=no`). valgrind는 자기가 흉내 내는 CPU 기능만 알려 주므로(AVX-512 없음) 암호 라이브러리가
  고르는 코드 경로가 기계마다 같습니다.
- 같은 바이너리로 세 번 잰 명령 수 차이: 암호·키 그룹·지문·비교 0.00%, 서명 0.41%(FN-DSA 거절 표본 추출), 저장 0.33%,
  적용 경로 0.14%(다중 스레드 런타임).
  다시 빌드하면 코드 배치가 바뀌어 1% 안쪽으로 움직일 수 있습니다(`aead_seal_open_1k` 33468 → 33708).

## 빈칸

- Tor 전달 지연(p95 3초)은 실제 Tor 망이 필요해 CI에서 재지 않습니다. 주간 `tor-leak.yml`이 실제 망에서 메시지를
  주고받지만 지연은 기록하지 않습니다.
- 메시지 목록 스크롤 60fps·음성 지연은 앱(웹뷰) 쪽이라 이 저장소의 Rust 시험에 없습니다.
- 시뮬레이션은 한 프로세스의 수십 노드까지입니다(기획서의 "수백 개"는 P6). 위치 찾기(DHT)·릴레이·NAT는 빼고 직접 연결만 씁니다.
- 큰 크루의 gossip은 놓친 이벤트를 주기 따라잡기(기본 5분)로만 채웁니다. 피어가 적은 노드·막 들어온 멤버가 메시에 늦게 드는
  문제(위)와 함께, 놓침을 빨리 알아채는 방법(예: 받은 이벤트의 부모가 비면 바로 따라잡기 외에, 머리 교환을 짧은 주기로)이 필요합니다.
- 전체 재키 몫은 `GetKeyShard`로 기기 몫만 받지만(약 2KB), 내주는 쪽은 블롭 조각을 가진 확정 기기와 그것을 받아 둔 멤버뿐입니다.
  4.5만 대가 한꺼번에 물으면 내주는 쪽마다 예산(기기마다 32KiB/s)으로 나눠 받으므로 몇 바퀴(20초 간격)에 걸칠 수 있습니다.
  조각 복제를 고르게 퍼뜨리는 일은 아직 없습니다.
- 확정 기기 표의 크루 칸은 기기 약 12만 대를 넘으면 넘기기 요청 하나(8MiB)에 들지 않아 그때는 넘기지 않고 전체 재키합니다(위
  "확정 기기 표 크기"). 크루 칸을 나눠 보내거나 봉인 블롭으로 넘기면 풀립니다.
- 데몬 경로 재기(`--keytree-daemon`)는 3,000대까지만 돌렸습니다(채우기만 30초). 4.5만 대는 아직 재지 않았고, 그 크기의
  바이트는 위 "실제 키 트리 대 모형"의 값입니다.
- 스냅숏 상한(32MiB)은 관리 설정을 한도까지 채운 크루에서 약 5.5만 명에 닿아 멤버 상한(65,536명)보다 낮습니다(멤버 하나 약
  410B, 그중 크루 키 사슬 상태 약 64B). 넘으면 체크포인트를 내지 않으므로 새 멤버가 처음부터 받고 해소기 항목이 다시 크루
  나이를 따라갑니다. 스냅숏을 압축하거나 관리 설정을 따로 받게 하면 풀립니다.
- 명령 수는 메모리·디스크 대기(SQLCipher fsync 등)를 보지 않습니다. 그런 회귀는 목표 시험의 벽시계 시간으로만 드러납니다.
